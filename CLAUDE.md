# OS 4.0: Forth MUD OS

A tiny bare-metal Forth operating system for AArch64 (QEMU `virt`, then AWS Graviton) whose end goal is a MUD served over TCP.

**The spec is [docs/brief.md](docs/brief.md). Read it before starting any milestone.** Where it is silent, pick the simplest option and log it in [DECISIONS.md](DECISIONS.md).

## Current status

See the milestone table in [Readme.md](Readme.md). Work strictly in milestone order; a milestone is done only when its acceptance test passes in the Docker image and is committed.

## Environment

- Host is Windows 11. There is no native toolchain on the host (no make, QEMU, gforth or binutils), and none should be added.
- Everything builds and runs inside the Docker image, via Rancher Desktop (dockerd/moby runtime) on WSL2.
- Build the image with `docker build -t os4 .`, then run `make` targets in the container against live source: `docker run --rm -v "${PWD}:/src" os4 make test`. See the Readme for the full command list.
- The repo currently lives under OneDrive. If git or bind mounts misbehave (lock files, slow I/O), suspect OneDrive sync first.

## Hard rules (from the brief)

- Never write to the boot disk or the app disk at runtime. Only the data disk is written.
- Never use `cache=unsafe` on the data drive.
- Never let a player-facing wordlist reach the full dictionary.
- Never store player data as Forth source, and never persist execution tokens.
- `sync` means `save-buffers`, then a device flush, then wait for completion. New player: record, `sync`, then index entry, `sync`.
- Every hardware access goes through HAL words (`net-send`, `net-poll`, `blk-read`, `blk-write`, `blk-flush`, `key`, `emit`). No driver details above `hal/`.
- Never expose the OS to the public internet while any `docs/tech-debt.md` entry marked **must fix before public** is open.
- Barriers (`dmb`/`dsb`) and other ordering-sensitive operations are named Forth words, never inline.

## Code conventions

- Most of the software is built in Forth: drivers, protocol stacks, the block layer, the MUD engine and tools. Assembly is only for primitives, the thinnest hardware access (register reads and writes, barriers), the bootstrap that loads the boot files, and measured hot spots; keep the Forth definition as the reference.
- Boot files: `forth/core.fs` (the language), `forth/output.fs` (the terminal vectors, output, strings, throw messages), the platform's drivers from `hal/`, `forth/blocks.fs` (block storage), `forth/errors.fs` (`.error`), `forth/tasks.fs` (multitasking, `ms`, the console's pausing `key`), `forth/random.fs` (`siphash`, `random`), `forth/crypto.fs` (SHA-256, HMAC, PBKDF2, password hashes), `forth/records.fs` (crash-safe records), `forth/net/*.fs`, `forth/interpreter.fs` (wordlists and the outer interpreter), `forth/sandbox.fs`, `forth/files.fs` (the app disk, read only: the standard file words and `include`), `forth/net/repl.fs` (the network REPL), `forth/app.fs` (starting the app), and `forth/start.fs`, which must stay last as it starts the app or the network REPL, then `quit`. `kernel.s` is assembled per platform (`HOSTED` defined for Linux) and its `bootfile` list picks the drivers.
- Drivers are Forth in `hal/`, behind HAL words. Blocks: `#disks blk-count blk-read blk-write blk-flush`, each taking a disk number (`virtio-blk.fs` bare metal; hosted `linux-blk.fs`, whose first argument lists the disk images separated by commas). Disks are told apart by what is on them, never by number (#101): the data disk by its header, the app disk by its FAT label `OS4APP`. Network: `net-up? net-mac net-send net-poll` (`virtio-net.fs`; hosted `linux-net.fs` carries frames as UDP). Entropy: `entropy` (`virtio-rng.fs`; hosted `linux-rng.fs`), which only `forth/random.fs` uses: everything else takes `random` or `siphash`. Register text for new throw codes with `n message: text`.
- The network stack is `forth/net/*.fs` (#65–67): `eth`, `arp`, `ip` (register protocols with `ip-handler!`), `icmp`, `udp` (`udp-bind`, `udp-send`, `udp-reply`; #73), and `net.fs` with the network task. Build outgoing packets in `tx-frame` and send without pausing in between (TD-15). They are embedded in the kernel and loaded in the order of the `bootfile` lines in `kernel.s`; add a new file there. Errors while loading report `<file>:<line>:`.
- The REPL is Forth (`interpreter.fs`); the assembly interpreter in `outer.s` only loads the boot files (DECISIONS.md #33). Each task has its own terminal: `type`, `key`, `key?` and `bye` go through user-area vectors (`'type` and so on), so a network session's REPL talks to its connection (`net/telnet.fs`). Per-task state (buffers, `errname`, `eof`, the search order) lives in the user area: nothing an interpreting task uses may be a global variable (#85-86).
- Words that wait on a connection (`get-line`, `send`, telnet input) give up after the task's `io-timeout` ms with -273; set it in any task serving a remote client (#94). Small binary state that must survive a crash goes in a record (`record!`/`record@`, two blocks each, #95); passwords are stored only as `hash-password` hashes and checked with `password?` (#96).
- Tasks share one dictionary. Words that extend it (`header`, `,`, `allot`, `:`) first `claim` it; the REPL releases it at the end of a line unless a definition is open (#88). Memory needed while the system runs (tasks, connections, any pool) must come from `reserve`, never `allot`, so it cannot land inside a half-built definition.
- Wordlists: `forth-wordlist`, `wordlist`, `get-order`/`set-order`, `definitions` and friends (#87). A player-facing wordlist is built with `expose` (see `sandbox.fs`); a task whose search order holds only it can reach nothing else. Boot-time lookups use the kernel's `latest` chain, so a boot file must not leave another wordlist current. Choose new word names with care: a later definition silently shadows an earlier one for everything compiled after it (`buffers` and `header` both bit us).
- Tasks are cooperative (#48–56): any word that waits must `pause` in its loop or sleep with `ms`/`stop`, and long computations must `pause` now and then, or the watchdog (default 5 s of 10 ms ticks) stops them with -262. Per-task state belongs in the user area: define it with `user`; reach another task's with `>user`.
- A system task's loop runs under `restarting` (#100), which reports whatever ended it and runs it again; loops in it catch per item (a frame, a connection) so one fault costs one item. `spawn` throws -275 beyond `max-workers`: a server that spawns per client must catch it and turn the client away.
- Anything shared that a task might use across a pause needs a `semaphore`; prefer `['] (word) some-lock locked`, which releases on errors too (#76). Block words hold `blocks-lock` and network senders hold `tx-lock` (#77–78): a new sending word must too. `free-conn` holds `conns-lock`, which the TCP timer sweep holds across its pauses (#109).
- Errors are `throw`n with standard codes and caught by `catch`; the REPL catches per line (#35–37). New error conditions should `throw` a code, not print and abort. Kernel errors throw through `try_throw` in `outer.s`. Mark words that only make sense inside a definition with `compile-only`.
- Every assembly primitive and every Forth word gets a stack-effect comment: `( n1 n2 -- n3 )`. The proofs check it against the code (DECISIONS.md #107): write `d` or `ud` for a double-cell item and `|` between alternatives, so the comment can be read.
- Proofs (`proofs/`, Lean 4, `docs/verification.md`, DECISIONS.md #105-107) are about the compiled dictionary: `tools/dump-words.fs` dumps it, `tools/forth2lean.py` generates `proofs/OS4/Words.lean`, `Specs.lean` and `Costs.lean`, each importing a module per boot file (`Words/NetTcp.lean`; never edit or commit those; #110), and `proofs/OS4/Machine.lean` models the primitives. A new primitive needs a model in `Machine.lean`, a stack effect proven in `PrimSpecs.lean`, and entries in `forth2lean.py`'s `PRIMS` and `EFFECTS`; until then, every word that uses it is left out of the proofs. Hand-written theorems go in their own files under `proofs/OS4/`, use the generated words' `.spec` theorems rather than unfolding callees, and never use `sorry`. Anything trusted, not proven, is listed in `Machine.lean`'s header. The system tasks' loops are proven to pause within bounded steps (`Yield.lean`, #108): a loop on their path that never pauses fails `make proofs` until it pauses or is listed in `proofs/yields.txt` with what bounds it, and so does a new table of xts they execute from.
- Forth source in blocks uses standard screens: 16 lines of 64 characters, and line 0 is an index comment. An app's source is plain files on its app disk, lines of up to 255 characters.
- Applications (#99): each lives in its own repository and depends on a tagged `os4` image (`os4:0.10`), whose `os4-app` script tests and runs it. Its files go on an app disk (FAT, read only, made by `tools/app-disk.sh`); at boot the base includes `app.fs` into `app-wordlist` and runs the app's `main`, which starts its tasks and returns. With no app the base starts the network REPL; an app serves its own ports through doors (`port-door ( port run-xt limit "name" -- )`, `serve-door`), each with a session cap, and `start-admin` gives it port 4001 alone (#103). `examples/hello` is the example. Keep the base general: nothing app-specific belongs in it.
- AArch64 registers: `x19` IP, `x20` data stack pointer, `x21` return stack pointer, `x22` cached TOS, `x23` user area. `x8`–`x15` are scratch, and `x24`–`x28` are scratch for primitives across subroutine calls. Hardware `sp` is reserved for exceptions and C calls and stays 16-byte aligned.
- Direct-threaded code: `NEXT` is `ldr x8, [x19], #8` then `br x8`. Non-primitive words start with an 8-byte code field `<insn>; bl <handler>` (DECISIONS.md #12).
- Kernel layout: `arch/aarch64/kernel.s` includes `outer.s`, `text.s`, `prims.s` and `compiler.s` as one assembly unit (the dictionary link chain needs this). Platform glue is a separate object: `linux.s` for the hosted build, `virt.s` (plus `vectors.s` and `virt.ld`) for bare metal on QEMU virt under Limine.
- Bare metal: Limine base revision 3, kernel in the higher half, devices reached through our own TTBR0 identity map of 0–1 GiB as Device memory (DECISIONS.md #23–25). Faults print a register dump and throw -256 (hosted: a signal report, then the same throw).
- The dictionary is RAM handed to `forth_cold` by the platform (largest usable region from Limine's memory map; hosted, an `mmap`), up to 128 MiB (#72). Code fields `bl` to handler trampolines at its start: use the `docol`/`dovar`/`docon` words, never the kernel's handler labels, when compiling code fields.
- Each task's stacks have limits, checked in colon calls, branches, loops and `pause` (#57). Kernel errors go through `try_throw` in `outer.s`, which unwinds to the `catch` frame first. Internal kernel words that only work inside definitions get `F_CONLY` in their `defcode` line.
- Assembly subroutines follow AAPCS64 (args in `x0`–`x7`, may clobber `x0`–`x15` and `x30`) and are named `*_sub`; HAL routines are `hal_key`, `hal_emit` and `hal_bye`.
- All text files use LF line endings (enforced by `.gitattributes`).

## Tests

- Tests are `tests/*.in` (Forth fed to the serial console) paired with `tests/*.out` (expected output), run headless under QEMU.
- `.out` files are transcripts: the banner, then each input line as the Forth echoes it, its output, and ` ok`. Generate a new one by running the `.in` file, then check every value by hand (and against gforth for standard words) before committing it.
- `make test` runs `tests/` and `tests/hosted/` on the hosted build (seconds), then `tests/` and `tests/baremetal/` over the serial console (under a minute; one VM per test, in parallel). `make test-hosted` or `make test-virt` runs one. `tools/run-tests.py` is the runner.
- `make proofs` checks every proof, re-proving only what changed (seconds unchanged, eight minutes after a change to `core.fs`, so not yet in `make test`, TD-30). Run it with Lake's build on a volume: `docker run --rm -v "${PWD}:/src" -v os4-lake:/src/proofs/.lake os4 make proofs`. Run it before a milestone is done and before merging a change to the base; a milestone is not done while it fails. Read `build/proof-findings.txt` after it: a stack comment that disagrees with its code is a bug in one or the other.
- A `<name>.filter` file next to a test is a sed script that masks build-dependent output, such as addresses in a register dump.
- Each test gets a fresh data disk of its own (in `build/test-disks/`, 1024 blocks, volume ID 42), and an app disk: made from `tests/<name>.app/` if that exists (FAT16 if it holds a file `.fat16`, else FAT32), else empty. `make test-app APP=/abs/dir` runs an app's tests, each with that app as its app disk. A line `\ --- reboot ---` in a `.in` file shuts down and boots again on the same disk (`tools/console-run.py`).
- Network tests: each test's NIC is wired to its own UDP ports; a `<name>.peer` file names a peer to run on that LAN (`tools/netpeer.py`, 10.0.2.2), whose findings follow `--- peer ---` in the transcript. Its `tcp` script is a raw-frame TCP client that can misbehave on purpose (drops, reordering); `tcp-attack` floods and forges as an off-path attacker; `hostile` sends malformed and random frames at every layer and rubbish over telnet (a new parser or protocol gets cases there); `soak` runs rounds of sessions and fails if memory or a pool grows after the first; its `repl` script drives telnet sessions and prints their transcripts; `connect PORT [LINE ...]` (for apps' tests, as `{tools}/netpeer.py`) connects, sends lines and prints what came back; `players PORT {name}.play` drives several telnet clients from a step file beside the test (`A connect`, `A> line`, `A? text` with ESC as `\e`, `A gone`, `A deaf` for a client that stops reading; clients can reconnect after a reboot). Ports 4000 and 4001 belong to the network REPL, so tests use others. `make ping-check` (privileged container) pings the OS with the real `ping`; `make tcp-check` runs `tools/tcp-check.py`, real sockets through QEMU's port forward, against the network REPL.
- `make run-tap` (privileged container) boots the OS on `tap0`, reachable from the container at 10.0.2.15: ping it from another shell with `docker exec`.
- `tools/blocks.py` formats data disks and lists or imports screens from the host: `python3 tools/blocks.py list build/data.img 5`.
- Drive a REPL interactively through a pseudo-terminal with `script -qec 'make -s run' /dev/null` (bare metal) or `script -qec 'make -s run-hosted' /dev/null` inside the container.
- Every feature adds tests, and the whole suite runs on every change.
