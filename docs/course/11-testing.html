Testing

How every feature is proved, on both builds, on every change: transcripts, isolated runs, scripted network peers that misbehave on purpose, and soak.

  • Transcripts, and the tools that run them side by side
  • Network peers: polite, clumsy, hostile
  • Soak, reference definitions, and a course that is tested too

This lecture is about how all of this is tested. The rule is simple: every feature adds tests, and the whole suite runs on every change, on both builds. The interesting part is how a small set of tools makes that cheap enough to keep doing.

We'll look at the transcript format again, and the two tools that run transcripts: one that runs many tests side by side, each in isolation, and one that drives a single system through its console, rebooting where asked.

Then the network peer, a scripted machine on each test's private network, which can be polite, clumsy, or downright hostile. And finally soak tests, reference definitions, and the check that keeps this course honest.

A test is a transcript

OS 4.0
: risky ( n -- ) dup 0= if -42 throw then . ;  ok
5 ' risky catch . 5 0  ok
0 ' risky catch . . -42 0  ok
tests/exceptions.out
  • The .in is typed; the .out must come back byte for byte
  • Write the .in, run it, then check every value by hand
  • Standard words: against gforth too
  • A failure shows a diff, and keeps the output as .actual

You met transcripts in lecture zero. Each test is a pair of files. The dot-in file is typed at the console. The dot-out file is the whole session as it should appear: the banner, each line echoed, its output, and ok.

The workflow matters as much as the format. Write the input. Run it to produce the output. Then, before committing, check every value in it by hand, and for standard Forth words, against gforth, an independent Forth. A transcript only proves something if a person has decided it's right.

When a test fails, the runner prints a diff between the expected and the actual output, and keeps the actual output in a dot-actual file beside the test, so you can look at the whole session.

Two builds, one suite

TEST_VIRT   = --cmd "$(CONSOLE) $(call VIRT_CMD,{disk},$(NET_TEST),{appdisk})"

Makefile › test
  • tests/ on both; tests/hosted/ and tests/baremetal/ on one each
  • Hosted: seconds. Bare metal: one VM per test, in parallel, under a minute
  • The same transcripts on both: the platforms must agree

The same tests run on both builds. The Makefile defines one command for each: the hosted binary under qemu-aarch64, or a full virtual machine booting through firmware and Limine. Each is given the test's disks and network ports.

Make test runs the course check, then the hosted suite, then the bare-metal suite. Tests in the tests folder run on both. A few that are about one platform, such as the register dump from a CPU fault, live in hosted or bare-metal folders of their own.

The hosted suite takes seconds. The bare-metal suite boots one virtual machine per test, many at once, and takes under a minute. Because the transcripts are shared, the two platforms are held to exactly the same behaviour.

Every test in its own world

    if output == expected:
        return name, True, ""
tools/run-tests.py › run_test
  • Setup commands make the disks; the test's command boots
  • {disk} {appdisk} {port} {peerport} {tools} in commands
  • A .filter sed script masks what changes per build

The runner, run-tests dot py, starts tests in parallel, and the trick that makes that safe is isolation. Every test gets a freshly formatted data disk of its own, a thousand and twenty-four blocks with volume ID forty-two. It gets an app disk, made from a folder named after the test if there is one, otherwise empty. And it gets its own pair of UDP ports, which carry its network.

Commands name those with placeholders in braces, filled in per test. So the same command line boots every test, each in its own little world, and no test can see another's disk or network.

Then the comparison is as blunt as can be: is the output exactly the expected bytes? If something in the output legitimately changes from build to build, like an address in a register dump, a filter file next to the test masks it first, with a few sed substitutions.

Driving the console

BANNER = b"OS 4.0\n"
CTRL_D = b"\x04"
REBOOT_MARKER = b"\\ --- reboot ---"
tools/console-run.py
0 >line \ written but never synced
\ --- reboot ---
10 11 index
tests/persist.in
  • Wait for the banner, then type; firmware can't eat the input
  • Ctrl-D at the end: the Forth powers off or exits
  • A reboot marker: shut down, boot again on the same disks
  • Carriage returns removed: one transcript for every platform

Each test's command is wrapped in console-run dot py, which makes a whole operating system behave like a program reading its input.

It holds the input back until the banner appears, so nothing typed is lost while the firmware and boot loader start up. Then it types the test, and finishes with Control-D, which ends the console's input and makes the system power off, or exit on the hosted build.

A line that says reboot, between dashes, splits the input. Everything before it runs, the system shuts down, and boots again on the same disks. The persist test uses this: it writes one block and syncs it, writes another without syncing, reboots, and checks that only the synced one survived.

It also strips carriage returns, so the serial console and the hosted terminal produce identical transcripts.

A machine on the other end

  • A .peer file names the script; it starts when the banner appears
  • It answers ARP and ping, and runs its script against the OS
  • Scripts: ping udp tcp repl hostile tcp-attack soak connect

Network tests need another machine on the network, so the tests provide one. Netpeer dot py is a complete, if small, network host written in Python, sitting at ten dot nought dot two dot two on each test's private network.

It doesn't use the host's network at all. The OS's frames are carried as UDP datagrams on the loopback address, one Ethernet frame per datagram. That's the format of QEMU's datagram network back end on bare metal, and of the hosted build's own network HAL, so the same peer works with both builds.

A test with a dot-peer file names a script. The peer starts as soon as the banner appears, answers ARP and ping like any host, and runs its script against the OS. What it finds is printed at the end of the transcript, after a line of dashes, so the peer's view is checked byte for byte too.

Peers that misbehave on purpose

  • tcp: 32 clients at once; one drops a segment, one reorders, one's sequence numbers wrap, one sends everything at once
  • tcp-attack: a SYN flood past the caps, forged resets and ACKs in and out of the window, an MSS of 0
  • hostile: malformed frames at every layer, then hundreds of random ones; a ping after each batch must still be answered
  • repl: sessions that hang up mid-line, go idle, guess passwords, find the door full
A new parser or protocol gets cases in hostile. A test that only sends good input proves half the job.

The peer's scripts are where the testing gets serious, because most of them misbehave on purpose.

The TCP script runs thirty-two clients at once. One drops a segment the OS sent, so the OS must retransmit. One sends out of order. One starts its sequence numbers just before they wrap. One sends all its lines in a single segment.

The attack script plays an attacker who can't see the traffic: it floods SYNs past the caps, forges resets and acknowledgements, and offers a maximum segment size of zero. Every connection must survive, or close exactly when it should.

The hostile script sends malformed frames at every layer, then hundreds of random ones, and checks after each batch that the OS still answers a ping. And the REPL script plays every awkward telnet user there is. The rule that comes out of this: a new parser or protocol gets cases in the hostile test. Proving that good input works is only half the job.

Soak: nothing may grow

round 2 grew 0 0 0
round 3 grew 0 0 0
round 4 grew 0 0 0
round 5 grew 0 0 0  ok
tests/soak.out
  • Five rounds: telnet sessions, TCP echo clients, pings, UDP
  • After each, once connections are gone: memory, pooled connections, workers
  • After round 1, all three must stay at 0
  • A leak shows up as a number, not a crash weeks later

Some bugs only show over time: a connection record that's never recycled, a task that never returns to the pool. A server that runs for weeks will find them. The soak test finds them in under a minute.

It runs five rounds of real work at once: telnet sessions, TCP echo clients, pings and UDP echoes. After each round, once every connection has closed, the OS itself reports three numbers against a baseline taken after the first round: dictionary memory used, connection records in the pool, and worker tasks.

The first round is allowed to grow, because pools fill up to their working size. After that, every number must be zero, round after round. A leak shows up as a number in a transcript, instead of a crash weeks into production.

Other ways to be sure

  • Reference definitions: tests/reference checks each assembly hot spot against its Forth definition
  • Real tools: make ping-check pings the OS with the real ping
  • Real stacks: make tcp-check runs real sockets, the host's own TCP, through QEMU's port forward
  • Apps: make test-app APP=… runs an app's tests with the app as its app disk

A few more kinds of check complete the picture.

Reference definitions, from lecture two: every hot spot that moved to assembly keeps its Forth definition, and the reference test checks that the two agree.

Real tools. Our own peer could share a misunderstanding with our own stack, so two make targets check against software we didn't write. Ping-check pings the OS with the real ping command over a virtual network device. Tcp-check runs real sockets, so the host's own TCP implementation talks to ours, through QEMU's port forwarding, with eight sandbox sessions and an admin session.

And apps get the same treatment: test-app runs an app's own transcripts on both builds, with the app as each test's app disk. That's what os4-app test calls.

The course is tested too

tools/check-course.py
  • Every excerpt in these lectures is real code, checked line by line
  • Every named word must still be defined; every tour step must still match
  • Part of make test: change the code, and the lecture must follow

Documentation drifts. Code moves on and the explanation stays behind, until it describes a system that no longer exists. This course is protected against that by its own check.

Every code excerpt you've seen in these lectures is marked with the file it came from, and the check confirms that every line of it is still a line of that file. Every word a slide names must still be defined there. Every step of every code tour must still find its place in its file, and every slide's Code button must point at a step that exists.

It runs as the first part of make test. So when the code changes, the lecture and the tour that describe it have to change in the same commit, or the suite fails.

Writing a test

  1. 1. Write tests/name.in: the commands, and a comment line saying what it covers
  2. 2. Add name.peer, name.app/ or name.filter if it needs them
  3. 3. Run it; the output lands in name.actual
  4. 4. Check every value by hand, and against gforth for standard words
  5. 5. Save it as name.out; run the whole suite; commit
docker run --rm -v "${PWD}:/src" os4 make test-hosted     # seconds
docker run --rm -v "${PWD}:/src" os4 make test            # everything

Here's the recipe for a new test. Write the input, starting with a comment line that says what the test covers, because that comment appears in the transcript too.

If it needs a network peer, an app disk, or a filter, add those files next to it. Run it: with no dot-out file yet, the test fails, but its output is saved as dot-actual.

Then the step that matters: read every value, and check it by hand, and against gforth for standard words. Only then save it as the expected output, run the whole suite, and commit.
