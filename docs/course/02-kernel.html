The kernel

How Forth actually runs on an ARM processor: five registers, two instructions between every word, and code fields written at run time.

  • The Forth machine in registers, and NEXT
  • Primitives, colon words and code fields
  • Trampolines, the instruction cache, and keeping Forth as the reference

Lecture one showed Forth from the outside. This one opens the lid. The kernel is about two thousand lines of ARM assembly, and its main job is to make Forth words run, quickly.

We'll see how the Forth machine lives in five processor registers, and how two instructions, called NEXT, move from one word to the next. Then the three kinds of word: primitives, colon definitions, and the defining words' children, all told apart by a code field at the start of each word.

Last, a few details that make this work on a modern processor: trampolines to reach far code, keeping the instruction cache in step with code written at run time, and why every assembly hot spot keeps a Forth version as its reference.

The Forth machine, in five registers

IP	.req	x19		// instruction pointer: the next cell of the current thread
DSP	.req	x20		// data stack pointer, grows down (TOS is cached, not in memory)
RSP	.req	x21		// return stack pointer, grows down
TOS	.req	x22		// top of the data stack
UP	.req	x23		// user area of the current task
arch/aarch64/macros.s
  • Callee-saved registers: a C routine or a system call leaves them alone
  • The top of the stack stays in a register: most words touch memory less
  • x8–x15 are scratch; the hardware sp is kept for exceptions

A Forth system is a small virtual machine, and here it lives in five registers. IP, the instruction pointer, says which word runs next. Two stack pointers say where the data stack and the return stack are. The top of the data stack is kept in a register of its own. And UP points at the user area of the task that's running, which you met in the lecture on tasks.

They're all callee-saved registers in the ARM calling convention. That means any ordinary subroutine, including the platform's own, promises to leave them alone, so the kernel can call out without saving anything.

Keeping the top of the stack in a register is a classic Forth speed-up. Plus, for example, needs one load from memory instead of two loads and a store.

Registers x8 to x15 are scratch for any primitive. The hardware stack pointer isn't used by Forth at all: it's kept for exceptions and calls into platform code.

Threaded code, and NEXT

.macro NEXT
	ldr	x8, [IP], #8
	br	x8
.endm
arch/aarch64/macros.s › NEXT
  • Load the next xt, step IP on, jump to it
  • Direct threading: an xt is the address of machine code

Here's a compiled colon word, square, in memory. After its header comes an eight-byte code field, which we'll come back to. Then the thread: one cell for each word in the definition, holding that word's execution token. Dup, star, and exit, which semicolon compiled at the end.

The instruction pointer walks along the thread. And this is how it moves: the macro NEXT. Load the cell IP points at into a scratch register, stepping IP on by eight bytes in the same instruction, then branch to that address. Two instructions. Every primitive ends with them, so control passes straight from one word to the next without returning anywhere in between.

This scheme is called direct threading. An execution token is the address of real machine code, so NEXT can jump to it directly. For a primitive, that's the primitive's own code. For anything else, it's the code field.

Primitives

	defcode	"dup", w_dup			// ( x -- x x )
	str	TOS, [DSP, #-8]!
	NEXT
	defcode	"+", w_plus			// ( a b -- a+b )
	ldr	x0, [DSP], #8
	add	TOS, x0, TOS
	NEXT
arch/aarch64/prims.s › dup, +
  • dup: one store, because the top is already in TOS
  • +: pop the second item, add into TOS
  • About ninety primitives: stack, arithmetic, memory, loops, the terminal
  • Each has a stack comment, like any Forth word

Primitives are the words written directly in assembly. Here are two.

Dup has a single instruction before NEXT. The top of the stack is already in the TOS register, so duplicating it just means storing a copy to memory, pushing it down a place. The register still holds the top.

Plus pops the second item from memory into a scratch register, adds it to the top of stack register, and that's the result, already where it needs to be.

There are about ninety primitives, covering the stacks, arithmetic, memory access, counted loops, and the terminal, plus a few measured hot spots. Each starts with a line called defcode, which lays down its dictionary header, and each has a stack comment, just like a Forth word.

Calling a colon word

docol:					// colon definition: run the thread in the body
	CHECK_STACKS
	RPUSH	IP
	mov	IP, x30
	NEXT
	defcode	"exit", w_exit, F_CONLY			// ( -- ) ( R: ip -- )
	RPOP	IP
	NEXT
arch/aarch64/compiler.s › docol
  • The code field's bl docol leaves the body's address in x30
  • docol: push IP, point IP at the body, carry on
  • exit: pop IP, carry on where the caller left off
  • A call costs a branch, a push and a NEXT

So what happens when NEXT jumps to a colon word like square? It lands on the code field, whose second instruction is a branch-and-link to a routine called docol.

Branch-and-link puts the address of the following instruction in register x30. The following instruction is exactly where the thread begins, the body of the word. So docol has everything it needs. It checks the stacks haven't overflowed, pushes the caller's instruction pointer on the return stack, points IP at the body, and runs NEXT. The first word of square starts.

At the end of the thread is exit, a primitive that pops the saved instruction pointer and runs NEXT. The caller carries on from where it left off.

That's the whole calling convention. A call to a Forth word costs one branch, one push and one NEXT. It's why Forth can afford to have so many small words.

Code fields: what kind of word is this?

dovar:					// CREATE, VARIABLE: push the body address
	PUSH	x30
	NEXT

docon:					// CONSTANT: push the value held in the body
	str	TOS, [DSP, #-8]!
	ldr	TOS, [x30]
	NEXT
arch/aarch64/compiler.s › dovar, docon
  • The same trick everywhere: x30 is the body
  • So execute never needs to know what kind of word it runs

Every word that isn't a primitive starts with an eight-byte code field: one instruction, then a branch-and-link to a handler. The handler decides what kind of word it is.

For colon words it's docol, as we've seen. For variables and anything made by create, it's dovar, which simply pushes x30, the body's address. For constants, docon pushes the value stored in the body instead.

Words made by a defining word that uses does are a little different. Their code field branches into the defining word itself, to a stub that does compiled there. The stub's first instruction copies x30, the child's body, into x9; then it branches to a handler called dodoes, which pushes the child's body and runs the Forth code that follows does.

The neat result is that every execution token is just an address to jump to. Execute, NEXT and the compiler never need to know what kind of word they're dealing with.

Reaching the handlers: trampolines

  • bl reaches 128 MiB either way
  • Four trampolines at the start of the dictionary jump the rest of the way
  • Compile code fields with the docol dovar docon words: they give the trampolines' addresses
	.equ	DICT_MAX, (1 << 27) - 4096
	.equ	TRAMPOLINE, 16			// bytes per trampoline: ldr x16, 8; br x16; .quad handler
arch/aarch64/kernel.s

There's a catch with code fields. An ARM branch-and-link can only reach a hundred and twenty-eight megabytes either way. On bare metal the kernel sits in the top of the address space and the dictionary is in ordinary RAM, much further apart than that.

The answer is trampolines. When the system starts, it writes four tiny stubs at the very start of the dictionary, one for each handler. Each loads the handler's full address into a register and branches to it. Code fields branch to the trampolines, which are always close by, and the trampolines jump the rest of the way.

That's also why the dictionary is capped at a hundred and twenty-eight megabytes: the furthest code field must still reach the trampolines at the start.

For you, this means one thing. When Forth code compiles a code field, it uses the words named docol, dovar and docon, which return the trampolines' addresses. Never the kernel's own labels.

Code written at run time

.macro SYNC_ICACHE addr
	dc	cvau, \addr
	dsb	ish
	ic	ivau, \addr
	dsb	ish
	isb
.endm
arch/aarch64/macros.s › SYNC_ICACHE
  • Data and instructions have separate caches
  • Clean the data cache line, invalidate the instruction cache line, then wait
  • One RWX memory region: the brief's flat address space

Every colon definition you type writes two new instructions, its code field, into memory. On an ARM processor that needs care, because data and instructions go through separate caches. The new instructions might sit in the data cache while the processor fetches stale ones from the instruction cache.

So after writing a code field, the kernel runs this sequence. Clean the data cache line out to the point where instruction fetches can see it. Wait. Invalidate the instruction cache line. Wait again. And finally an instruction barrier, so the processor discards anything it fetched early.

It also means the dictionary must be readable, writable and executable at once. On bare metal it's one flat region mapped that way; hosted, it's a block of memory asked for with all three permissions. That's a deliberate choice from the brief: one simple address space, no protection between parts of the system.

Assembly words in the dictionary

	.balign	8
\label\()_nt:
	.quad	link
	.set	link, \label\()_nt
	.byte	\flags + 9f - 8f
8:	.ascii	"\name"
9:	.balign	8
\label:
.endm

  • Some kernel words are threads written by hand

	defword	":", w_colon			// ( "name" -- ) start a colon definition
	.quad	w_parsename, w_header, w_docol, w_cfcomma, w_hide, w_rbracket, w_exit
arch/aarch64/compiler.s › :

The kernel's words have to be in the dictionary too, so the assembler builds their headers. This macro, defcode, lays down exactly the header from lecture one: the link to the previous word, the flags and length, and the name, padded to eight bytes. Then the label where the code begins. Each use updates a symbol called link, so the chain grows as the file is assembled.

A few kernel words are colon definitions written by hand as a list of addresses. Here is colon itself: parse a name, lay down a header, compile a code field branching to docol, hide the word until it's finished, and turn compiling on.

Because one symbol threads through every word, the kernel's assembly files are included into kernel dot s and assembled as a single unit. The last header becomes the initial value of latest, and the Forth boot files carry on the chain from there.

Forth stays the reference

	// ( addr u nt -- nt' | 0 ) the newest word named addr u from nt back, ignoring
	// case and hidden words. A measured hot spot: interpreter.fs has
	// SEARCH-LIST-REF, the Forth definition, which tests/reference checks.
	defcode	"search-list", w_searchlist
arch/aarch64/compiler.s › search-list
: agree ( addr u -- flag ) 2dup latest @ search-list >r latest @ search-list-ref r> = ;
tests/reference.in
  • Hot spots in assembly: search-list, cmove, fill, um/mod, SHA-256's block
  • Each keeps its Forth definition, and a test that the two agree

The rule is Forth first. But a few words turned out to be too slow in Forth, measured, not guessed. Looking words up in the dictionary is one: it runs for every word you type and every word in every boot file.

When a word moves to assembly, its Forth definition stays. Here, the comment on the assembly search-list points to search-list-ref, the Forth version, in the interpreter file.

And a test checks they agree. This line from the reference test defines a word that looks a name up both ways and compares the answers. It's run with words that exist, words in a different case, and words that don't exist.

The same goes for the other hot spots: moving and filling memory, a division, and the inner block of SHA-256. The Forth is the specification; the assembly is an optimisation that must keep matching it.
