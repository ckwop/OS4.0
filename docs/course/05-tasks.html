Tasks

How one CPU serves the console, the network and every telnet session at once, by taking turns.

  • What a task is, and how pause switches between them
  • Sleeping, waking, and giving a task work
  • Sharing safely, failing safely, and the watchdog

Welcome to lecture five, on tasks. This is the part of OS 4.0 that lets one processor look after many things at once: the console you type at, the network stack, and every telnet session that connects.

We'll look at what a task actually is in memory, and at the word pause, which is how the system moves from one task to the next. Then we'll see how a task sleeps, how it's woken, and how it's given work to do.

Finally, three things that keep the system trustworthy: how tasks share data without trampling on each other, what happens when a task fails, and the watchdog, which catches a task that never gives anyone else a turn. One CPU, many jobs, taking turns

  • A task runs until it calls pause, or a word that waits
  • Between two pauses it is alone: nothing changes under it
  • The price: a task that never pauses stops everyone

Here's the whole idea in one picture. Time runs from left to right, and there are four tasks: the console, the network task, and two telnet sessions. Only one runs at any moment, and they take turns.

The orange marks are the important part. A task runs until it calls pause, or calls a word that waits, such as reading a key or waiting for a network packet. Every waiting word calls pause in its loop. This is cooperative multitasking: each task decides when to give way. Nothing ever interrupts a task to run another one.

That buys something precious. Between two pauses, a task is completely alone. No other task can change a variable under its feet, so most code needs no locking at all. That's why the network stack and the interpreter can be written so simply.

The price is just as clear. A task that loops forever without pausing would stop the whole machine. We'll come back to how the system protects itself from that at the end of the lecture.

A task is a block of memory

  • Its size is the sum of the four parts
  • A user variable lives in the user area: one copy per task
  • Memory comes from reserve, never allot
/user /dstack + /rstack + /buffers + constant /task

: new-task  ( name len -- task )  \ a task, asleep, at the end of the ring
  /task reserve >r                                \ not from the dictionary: see CLAIM
  up@ r@ /user move                               \ start from a copy of this task's
forth/tasks.fs › new-task

So what is a task? Just a block of memory, about five and a half kilobytes. At the top is the user area, five hundred and twelve bytes holding everything that belongs to this task alone: its number base, whether it's compiling, its error handler, its search order, and the vectors that say where its terminal is. Then come its own data stack and return stack, two kilobytes each, and some buffers for text and numbers.

Here's how a task is made. Its size is the sum of those four parts. New-task reserves that much memory, then copies the user area of the task that created it, so a new task starts life with its parent's settings.

Register x23 always points at the user area of the running task. When you define a variable with the word user instead of variable, every task gets its own copy, found through that register. Anything an interpreting task uses must be a user variable, never a global.

Notice that the memory comes from reserve, which takes it from the far end of the dictionary space. It never uses allot, because a task can be created while another task is halfway through compiling a definition, and its memory must not land in the middle of that definition.

The tasks form a ring

  • task-link: the next task in the ring
  • New tasks join just before the console
  • task-status: 0 ready, 1 not; task-wake: when to wake
  • Try .tasks on the console to see the ring

All the tasks are linked into a ring. On a freshly booted system you'll find the console, the network task, and the two listeners of the network REPL, plus a worker task for each telnet session that's open.

The link lives in each task's user area, in a field called task-link. A new task is inserted just before the console, so the ring always starts and ends there. Pause simply walks round this ring, going clockwise in the picture, looking for the next task that can run.

How does it know which can run? Two more fields. Task-status is zero when the task is ready, and one when it isn't. Task-wake holds the time at which a sleeping task should wake up, or zero if it's waiting for someone else to wake it.

You can see the ring for yourself. Type .tasks at the console and it lists every task with its state: running, ready, sleeping, or stopped.

pause: the whole task switch

  RPUSH  IP
  str    TOS, [DSP, #-8]!
  str    DSP, [UP, #U_SP]
  str    RSP, [UP, #U_RP]
  mov    x28, UP          // the search ends back at this task
1: ldr   UP, [UP, #U_LINK]
  ldr    x0, [UP, #U_STATUS]
  cbz    x0, 3f           // ready
  …
2: cmp   UP, x28
  b.ne   1b
  …
  bl     hal_idle
  b      1b
3: ldr   x1, =var_task_ticks
  str    xzr, [x1]
  ldr    DSP, [UP, #U_SP]
  ldr    RSP, [UP, #U_RP]
  ldr    TOS, [DSP], #8
  RPOP   IP
  NEXT
arch/aarch64/prims.s › pause
  • Save: the place in the code, the top of stack, both stack pointers
  • Find: follow the link to a task that is ready, or whose time has come
  • Restore: its stack pointers, its place in the code, and carry on
  • Nothing ready? hal_idle waits for the next 10 ms tick

This is pause itself, one of the few words written in assembly, because it runs constantly. It has three steps. First, save. The running task's place in the code, the instruction pointer, goes onto its own return stack, and the cached top of its data stack goes onto its data stack. Then both stack pointers are written into its user area.

Second, find. The user-area register is replaced by the link to the next task, and its status is checked. If the status is zero, it's ready. If it's asleep with a wake time that has passed, it's made ready. Otherwise, on round the ring.

Third, restore. Load that task's stack pointers from its user area, pop its saved top of stack and instruction pointer, and run the next word. That task now carries on from exactly where it last paused. Notice how little there is to switch: a Forth task's whole state is its instruction pointer, its two stacks and its user area.

If the search comes all the way round and nothing can run, the processor waits for an interrupt. The timer ticks every ten milliseconds, so a sleeping task is never more than one tick late, and an idle machine uses almost no power.

Sleeping and waking

  • ready: runs on its next turn
  • sleeping: until a time
  • stopped: until another task wakes it
  • A listener stops in accept-connection; the network task wakes it when a client arrives
: stop   ( -- )  1 task-status !  0 task-wake !  pause ;   \ until another task wakes this one
: wake   ( task -- )  0 swap task-status field! ;
: ms     ( n -- )  counter-hz 1000 / *  counter +  task-wake !  1 task-status !  pause ;
forth/tasks.fs › ms

A task is in one of three states. Ready means it will run on its next turn. Sleeping means it's waiting for a time. Stopped means it's waiting for another task to wake it.

All three words are tiny Forth definitions. ms works out the counter value some milliseconds from now, stores it as the wake time, marks the task not ready, and pauses. Pause will make it ready again once the counter passes that value. Stop marks the task not ready with no wake time at all, so only another task can bring it back. And wake just sets another task's status to zero, through the field-store word, which reaches into that task's user area.

Here's a real example. A listener waiting for a telnet connection is stopped inside accept-connection, costing nothing. When a connection arrives, the network task queues it and wakes the listener, which runs on its next turn.

Giving a task work

: run-task  ( i*x xt -- )  \ a task's whole life: run xt, report how it ended, sleep
  catch ?dup if  ['] report catch if drop then  then   \ its terminal may be gone
  unclaim  0 state !
  pooled @ if  free-tasks @ next-free !  up@ free-tasks !  then   \ back to the pool
  begin stop again ;
forth/tasks.fs › run-task
  • A new task is simply a task that hasn't run yet
  • ' word task start
  • x ' word task start-with

Every task spends its whole life in this one word, run-task. It runs the work it was given under catch. If the work throws an error, it reports it, carefully, because a session's terminal may already be gone. Then it tidies up, returns itself to the pool if it came from one, and stops for good.

The neat part is how a task gets into run-task in the first place. Start doesn't call anything. It lays out the new task's stacks exactly as if the task had paused: the work's execution token on the data stack, and on the return stack the address of a cell that holds run-task. The next time pause comes round to that task, it restores those stacks and carries on, and carrying on means running run-task. There's no special first-run path at all: a new task is simply a task that hasn't run yet.

To use it, give start an execution token and a task. Start-with also passes one value, such as the connection a session should serve.

The pool: a task per client, within limits

: spawn  ( x xt -- task )  \ run xt with x in a pooled task
  free-tasks @ ?dup if
    dup next-free >user @ free-tasks !
  else
    workers @ max-workers @ < 0= if -275 throw then
    s" worker" new-task  true over pooled field!  1 workers +!
  then
  dup >r start-with r> ;
forth/tasks.fs › spawn

Servers want one task per client, so each session has its own stacks and its own terminal. Making a new task every time would slowly eat memory, so there's a pool.

Spawn first looks for a worker that has finished its previous job. Remember that run-task puts a pooled task back on the free list when its work ends. If there isn't one, spawn makes a new worker, but only while there are fewer than sixty-four. Beyond that it throws -275, no free task.

That limit matters. A flood of connections can't exhaust memory; at worst, new clients are turned away. Which means anything that spawns must be ready for that throw. The REPL's listener catches it and drops just that connection, rather than dying itself.

Sharing across a pause: semaphores

: get  ( sem -- )
  dup @ up@ = if  cell+ 1 swap +!  exit  then
  begin dup @ while pause repeat
  up@ over !  cell+ 1 swap ! ;
: locked  ( i*x xt sem -- j*x )  dup >r get  catch  r> release  throw ;
forth/core.fs › locked
  • The rule: anything shared that is used across a pause needs a lock
  • ['] (word) some-lock locked releases even on errors
  • The locks in the base: blocks-lock, tx-lock, files-lock, and claim for the dictionary

Earlier I said that between two pauses a task is alone, so it needs no locks. The flip side is the rule on this slide: if a task uses something shared across a pause, it does need one. Reading a disk block is the classic case. The task asks the device for the block, then pauses while it waits, and another task must not grab that buffer in the meantime.

A semaphore here is two cells: which task holds it, and how many times. Get waits, pausing politely, until nobody holds it, then takes it. If the task already holds it, get just counts up, so a word that holds a lock can call another word that takes the same lock. Locked is the way to use one: it runs a word holding the semaphore, and releases it however that word ends, even if it throws an error.

The base has a few of these. Blocks-lock guards the block buffers, tx-lock the network's send buffer, and files-lock the app disk. And the dictionary itself is claimed by whichever task is compiling, so two telnet sessions can't build definitions into each other.

When a task fails, it costs one item

: restarting  ( xt -- )  \ run xt for ever
  begin
    dup catch ?dup if  ['] report catch if drop then  then
    1 restarts +!  1000 ms
  again ;
forth/tasks.fs › restarting
: net-loop  ( -- )
  begin
    ['] tcp-timers catch if  1 net-errors +!  then
    rx-frame net-poll ?dup if
      ['] frame-in catch if  drop 1 net-errors +!  then  pause
    else  10 ms  then
  again ;
forth/net/net.fs › net-loop
Two layers: catch per item inside the loop, and restarting around the loop.

Errors in Forth are thrown and caught, and tasks use that in two layers.

The outer layer is restarting. System tasks, like the network task and the REPL listeners, don't run their loop directly. They run it under restarting, which catches whatever ended the loop, reports it, waits a second so a persistent fault can't spin, and starts the loop again. A service can stumble, but it can't stop for good.

The inner layer is inside the loop itself. Here's the network task's loop. Every received frame is handled under its own catch, and so are the TCP timers. A malformed packet that trips an error costs exactly one packet, counted in net-errors, and the next frame is handled as normal. The same pattern runs through the base: catch per item, a frame or a connection, so one fault costs one item.

The watchdog

  • Counts ticks the task has had, not clock time
  • The error lands in that task alone: the console, a session, a worker
: watchdog  ( ms -- )  dup if 10 / 1 max then  watchdog-limit ! ;   \ in 10 ms ticks; 0 turns it off
5000 watchdog
forth/tasks.fs › watchdog

Now the safety net for cooperative multitasking. The timer interrupts every ten milliseconds, and each tick adds one to a count for the running task. Every time a task pauses, the count goes back to zero; you saw that in pause's restore step.

A task that never pauses lets the count climb, and when it reaches the limit, five hundred ticks or five seconds by default, the timer handler makes that task throw -262. It's an ordinary error, so it's caught like any other: by the REPL if it was the console, by run-task if it was a worker. The rest of the system never notices.

Why count ticks rather than measure the time? Under emulation the host sometimes stalls the whole virtual machine. With a clock, the stall would be blamed on whichever task happened to be running, perhaps in the middle of holding a lock. Ticks that never arrived are simply never counted.

Try it on the console

\ a task of your own, asleep until started
task clock
: tick-tock  ( -- )  5 0 do  ." tick "  1000 ms  loop ;
' tick-tock clock start            \ ticks while you keep typing
.tasks                             \ console running, clock sleeping, …
\ a word that never pauses
: spin  ( -- )  begin again ;
spin                               \ five seconds later: stopped by the watchdog

Boot with docker run --rm -it os4.

Time to try it. Boot the OS and make a task called clock. Define a word that prints tick five times, sleeping a second between each, and start it in the clock task. You can keep typing at the console while it ticks, because every time the clock sleeps, the console gets its turn. Type .tasks while it runs and you'll see it sleeping.

Then define spin, a loop with no pause in it, and run it. The console goes quiet for five seconds, then the watchdog stops it, the REPL reports the error, and you're back at the prompt. Everything else carried on underneath.
