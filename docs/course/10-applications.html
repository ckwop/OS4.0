Applications

How an app lives on its own disk, in its own repository: a read-only FAT file system in Forth, include, start-up, and the os4-app tool.

  • The base and the app: two repositories, one image
  • The app disk: FAT, read only, in about 270 lines of Forth
  • Loading and starting an app, and testing it

OS 4.0 is a base for applications. The MUD will be the first, but it won't live in this repository. This lecture shows how an application is packaged, found, loaded and started, and how it's tested without touching the base.

We'll start with the split between the base and an app. Then the app disk: a FAT file system, read by a small driver written in Forth, which only ever reads. Then include, which loads Forth source from files, and the few lines that start an app at boot.

Finally the example app, hello, and the os4-app tool that tests and runs any app against a versioned image of the base.

The base and the app

  • Nothing app-specific in the base; nothing of the base's source in an app
  • examples/hello stands in for an app repository

There are two kinds of repository. This one is the base: the kernel, the boot files, the drivers, the tools and the tests. Building it makes a Docker image, tagged with a version, such as os4:0.9b, which holds the built base and a tool called os4-app.

An application lives in a repository of its own: an entry point called app dot fs, the files it includes, and its own transcript tests. It never contains the base's source. It names a tagged image, and uses that image to test and run itself.

That boundary works both ways. The base stays general, with nothing in it for one particular app. And the app pins a version, so the base can change without breaking it until the app chooses to move up.

In this repository, examples slash hello plays the part of an app's repository.

The app disk

if [ -n "$dir" ] && [ -e "$dir/.fat16" ]; then
    mkfs.fat -C -F 16 -s 1 -n OS4APP "$img" 16384 >/dev/null
else
    mkfs.fat -C -F 32 -n OS4APP "$img" 65536 >/dev/null
fi
tools/app-disk.sh
  • FAT, made with ordinary tools: mkfs.fat, mcopy
  • Labelled OS4APP; the app's directory copied in
  • Attached read-only; the OS never writes it
  • What the app writes goes in blocks on the data disk

An app reaches the machine as a disk of its own. The script that makes it is a few lines: format an image as FAT, labelled OS4APP, and copy the app's directory onto it. FAT thirty-two normally; FAT sixteen if the app asks for it, which the tests use to exercise both.

Why FAT? Because ordinary tools on any computer can make one, and so can cloud tooling. Nobody has to learn a custom format to ship an app.

The system only reads the app disk. QEMU attaches it read-only as well, belt and braces. An app that needs to keep data, player records for a MUD, say, writes it in blocks on the data disk, through the storage layer from lecture six. That's the clean boundary: FAT for what's only read, blocks for what's written.

Finding the app disk

: find-app-disk  ( -- )  \ into APP-DISK, once
  fat-looked @ if exit then  true fat-looked !
  #disks 0 ?do  i app-disk !  ['] fat-volume? catch if false then  if unloop exit then  loop
  -1 app-disk ! ;
forth/files.fs › find-app-disk
  • fat-volume? reads the boot sector: geometry, FAT type, and the label
  • FAT16 or FAT32 by cluster count; FAT12 refused (-277)
  • Every read goes through the block HAL and one 1 KiB cache, under files-lock

Just like the data disk, the app disk is found by what's on it. Find-app-disk tries each disk in turn. Fat-volume-query reads its boot sector, checks the signature and that the numbers are sane, works out where the tables and the data are, and finally checks the volume label. The first disk labelled OS4APP wins. A disk whose boot sector is rubbish just throws, which is caught and counts as no.

Whether it's FAT sixteen or FAT thirty-two is decided the official way, by counting clusters. FAT twelve, used on tiny disks, isn't supported, and gets an error that says so.

Notice there's no new driver here. The file system reads through the same block HAL as everything else, one kilobyte at a time, with a one-block cache, and a lock so that only one task is on the app disk at once.

Clusters and chains

: next-cluster  ( cluster -- cluster' | 0 )  \ 0 at the end of the chain
  fat-bits @ 32 = if
    4 * fat-start @ + fat-byte le32 $0fffffff and  dup $0ffffff8 u< 0= if drop 0 exit then
  else
    2* fat-start @ + fat-byte le16  dup $fff8 u< 0= if drop 0 exit then
  then ?cluster ;
forth/files.fs › next-cluster

FAT stores files in clusters, runs of sectors. A file's directory entry names its first cluster. The file allocation table, the FAT that gives the system its name, holds one entry per cluster: the number of the next cluster in the file, or a marker for the end.

Next-cluster reads that entry, four bytes for FAT thirty-two and two for FAT sixteen, and turns the end marker into zero. Then it checks the result is a real cluster number, because the disk could be damaged, or deliberately made wrong.

One more guard sits in the code that follows chains. A broken chain could loop back on itself, and a naive reader would go round for ever. So it counts the clusters it has followed, and if that ever exceeds the number of clusters on the disk, it throws an I O error instead. Even a read-only file system has to distrust its input.

Paths and names

: walk-path  ( addr u -- )  \ the file or directory at the path
  ?volume  0 p-cluster !  unbounded p-size !  true p-dir? !
  begin skip-slashes dup while
    p-dir? @ 0= if -38 throw then
    split lookup
  repeat 2drop ;
forth/files.fs › walk-path
  • Start at the root; one directory per /
  • Long file names are read; short ones shown as NAME.EXT
  • Names match without regard to case
  • Not there: -38, non-existent file

Opening a file starts with its path. Walk-path begins at the root directory and takes the path apart at each slash. For each part, it looks the name up in the current directory, which must really be a directory, and moves into what it found.

Directory entries come in two flavours. Every file has a short name, eight characters and a three-character extension, a relic of the nineteen-eighties. Most also have a long name, stored in extra entries just before it, thirteen characters at a time. The reader puts long names back together, and falls back to the short one when there isn't a long one.

Names are matched without regard to case, as Windows does, so an app can include greeting dot fs in whatever case it likes. A name that isn't found throws -38, the standard code for a file that doesn't exist.

The standard file words

: open-file  ( addr u fam -- fileid ior )
  drop  ['] (open-file) ['] lock-files catch ?dup if  >r drop 2drop 0 r>  else 0 then ;
forth/files.fs › open-file
variable rooms
s" data/rooms.txt" r/o open-file throw  rooms !
pad 255 rooms @ read-line throw  ( len flag )
rooms @ close-file throw
  • Standard Forth: open-file read-file read-line file-size close-file
  • An ior: 0, or a throw code to pass to throw
  • Open files from a pool of 16, in reserved memory (-276 beyond)
  • r/o is the only access method there is

Apps use the standard Forth file words, so Forth programmers already know them. Open-file, read-file, read-line, file-size and close-file.

The standard words don't throw. They return an I O result, called an ior, alongside their results: zero for success, or an error code. In OS 4.0 that code is a throw code, so the usual idiom is to pass it straight to throw, as the example here does. Inside, each word does its work under catch and the files lock, and turns any error into the ior.

Open files come from a pool of sixteen, in memory taken with reserve, so a leaked file can't grow the dictionary. A seventeenth open fails with too many open files.

And read-only is the only access method. There's no word to write a file.

include: loading source from files

: include-lines  ( f -- )
  >r  begin  r@ f.buf /line r@ read-line throw  while
    dup /line = if -278 throw then
    #tib !  r@ f.buf 'tib !  0 >in !  1 r@ f.line# +!
    'interpret @ execute  pause
  repeat  drop r> drop ;
forth/files.fs › include-lines
  • A line at a time into the file's own buffer, then interpret
  • The file stays on the return stack: definitions may span lines
  • Lines up to 255 characters (-278 beyond); CR LF is fine
  • An error: app.fs:12: from the innermost file

Include loads Forth source from a file. Underneath, include-lines reads the file a line at a time, into a buffer that belongs to that open file. It points the interpreter's input at the line, counts the line for error reports, and interprets it, pausing after each line so other tasks keep running during a long load.

One detail is worth noticing. The file handle is kept on the return stack, not the data stack. That's because a colon definition can span several lines, and while it's open the compiler keeps its own values on the data stack, for if and begin and so on. A file handle there would be buried, or worse, mistaken for one of them. That was a real bug, caught by a test with a multi-line definition.

Lines can be up to two hundred and fifty-five characters, and Windows line endings are handled. And an error inside an included file reports the file name and line, from the innermost file, so a mistake in a nested include points at the right place.

Starting an app

: (boot-app)  ( -- )
  s" app.fs" included
  s" main" app-wordlist search-wordlist if execute then ;
: boot-app  ( -- )
  forth-wordlist app-wordlist 2 set-order  app-wordlist set-current
  ['] (boot-app) catch  forth-wordlist set-current
  ?dup if  ." app: " .error reset  then ;
: start-app  ( -- )  app? if boot-app else start-repl then ;
forth/app.fs › boot-app
  • The app's words go in app-wordlist, searched first
  • main, if the app defines one, starts its tasks and returns
  • An error is reported and the console comes up anyway; no app: the network REPL

Here's the whole of app start-up. Start dot fs calls start-app as the system boots. If the app disk holds app dot fs, boot-app runs; otherwise the base starts the network REPL, as before.

Boot-app makes a wordlist for the app, puts it first in the search order, and makes it current, so every definition the app makes goes there, apart from the base's. Then, under catch, it includes app dot fs, and, if the app defined a word called main, runs it. Main's job is to start the app's tasks and return promptly.

If anything goes wrong, the error is reported with its file and line, prefixed with app, and the system carries on: the console comes up regardless. A broken app never stops the machine from booting, so you can always get in and look.

hello: an example app

: greeter  ( -- )  \ for ever: RESTARTING runs it again if it ends
  5000 io-timeout !                     \ a client that stops reading is given up
  hello-port listen
  begin
    hello-port accept-connection  dup ['] greet catch if  drop drop-connection  else drop then
  again ;

task hello-task
: main  ( -- )
  ['] greeter ['] restarting hello-task start-with
  ." hello: listening on port " hello-port (.) type cr ;
examples/hello/app.fs › main
  • A task of its own, supervised by restarting
  • An io-timeout, and a catch per client: the habits from lectures 5 and 8

Hello is the example app. It greets whoever connects to port five thousand, tells them which visitor they are, and hangs up. Its app dot fs includes a second file, greeting dot fs, just to show include at work.

Main does what main should: it starts the greeter in a task of its own, under restarting, so the greeter comes back if it ever stops, and prints a line to say it's listening. Then it returns, and the console comes up.

The greeter shows the habits from earlier lectures, in a real app. It sets an IO timeout, so a client that stops reading is given up after five seconds. And each client is greeted under its own catch, so a client that misbehaves costs that client's connection, and the greeter carries on to the next.

Testing and running an app

OS 4.0
hello: listening on port 5000
…
--- peer ---
peer: 5000| Hello from an OS 4.0 app. You are visitor number 1
peer: 5000: closed
examples/hello/tests/hello.out
  • The same transcript tests as the base, with the app as the app disk
  • A .peer file connects to the app and reports what came back
  • os4-app test: both builds. os4-app run . 5000: boot it, port forwarded
docker run --rm -v "${PWD}:/app" -w /app os4:0.9b os4-app test

An app is tested exactly the way the base is: transcript tests in its tests folder, run on both builds, with the app's own directory made into the app disk for each test.

Hello's test shows the app's start-up line after the banner. Its peer file runs the network peer's connect script, which connects to port five thousand and reports what it was sent. That report appears after the dashes at the end of the transcript: the greeting, then the connection closing.

The os4-app tool in the image does the work. Test runs the tests on both builds. Run boots the app on bare metal with the ports you name forwarded, keeping its data disk in the app's build folder between runs.

Try it

# in examples/hello
docker run --rm -v "${PWD}:/app" -w /app os4:0.9b os4-app test
docker run --rm -it -p 127.0.0.1:5000:5000 -v "${PWD}:/app" -w /app os4:0.9b os4-app run . 5000
# then, from Windows:  telnet localhost 5000
\ on the console of a running app
dir /                                  \ the app disk's files
greeted @ .                            \ visitors so far
include greeting.fs                    \ load a file again

Build the image from the base first, then go into the hello folder. The first command runs its tests on both builds. The second boots it with port five thousand published to your machine, and telnet gets the greeting.

On the console of the running app, dir lists the app disk, the app's own variables are right there to look at, and include loads a file from the app disk again. The full Forth is always under the app, for the operator.

Questions to think about…

  1. Why keep the app's words in their own wordlist, searched first? What could go wrong if they went straight into forth-wordlist?
  2. A MUD needs a world that builders edit while it runs. Which parts belong on the app disk, and which in blocks? Why?
  3. main loops for ever instead of returning. What happens at boot, and who notices?

That's applications. An app is files on a read-only FAT disk, in its own repository, tested against a tagged image of the base. The base finds the disk by its label, reads FAT in a few hundred lines of Forth, includes app dot fs into the app's own wordlist, and runs main.
