The REPL and security

Forth over telnet, for strangers and for the operator: terminals per task, doors with limits, a sandbox, passwords and randomness.

  • A terminal for every task, and telnet
  • Doors, sessions, wordlists and the sandbox
  • Passwords, randomness, and the rules for going public

OS 4.0 serves its Forth prompt over the network. Port four thousand is a sandbox that anyone may use. Port four thousand and one is the full Forth, for the operator, behind a password. A MUD is exactly this shape: strangers get a limited language, and the owner gets everything.

This lecture shows how that's built. First, how each task gets its own terminal, so a REPL can talk to a network connection as easily as to the console. Then the doors that admit sessions, with limits, and the wordlists that decide what a session can see.

Last, the security underneath: how the admin password is stored and checked, where the system's random numbers come from, and the rules that must hold before the system faces the internet.

Every task has a terminal

user 'type   ' console-type 'type !
user 'key    ' (console-key) 'key !
user 'key?   ' console-key? 'key? !
user emitted                          \ EMIT's character
: type    ( addr u -- )  'type @ execute ;
forth/output.fs › type
  • type, key, key? and bye call through vectors in the user area
  • So the same REPL, accept, . and words serve any terminal

The trick that makes a network REPL easy is this. Type, which every output word ends in, doesn't talk to hardware. It fetches an execution token from a user variable called tick-type, and runs it. Key and key-query work the same way, and so does bye.

Because those vectors live in the user area, every task has its own. The console's point at the serial port. A telnet session's task points them at its own TCP connection, through the telnet code.

So the REPL needs no network code at all. The same interpret loop, the same accept for reading a line, the same dot and words, all work on whichever terminal the running task has. And because they're per task, two sessions can be typing at once, each seeing only its own output.

Just enough telnet

create character-mode  iac c, will c, opt-echo c,  iac c, will c, opt-sga c,
: telnet-terminal  ( conn -- )  \ this task's terminal is conn from now on
  dup term-conn !  0 after-cr !
  ['] telnet-type 'type !  ['] telnet-key 'key !  ['] telnet-key? 'key? !
  character-mode 6 rot send ;
forth/net/telnet.fs › telnet-terminal
  • "I will echo, I will suppress go-ahead": the client sends each key as typed
  • So accept echoes and edits, exactly as on the serial console
  • In: commands skipped, CR LF made one line end. Out: LF becomes CR LF

Telnet is the oldest remote terminal protocol, and the system speaks just enough of it. When a session starts, telnet-terminal points the task's vectors at the connection, and sends six bytes of negotiation: I will echo, and I will suppress go-ahead.

Those two options put the client into character mode. It stops echoing locally and sends each key as it's pressed. That's exactly what the serial console does, so accept, the word that reads a line, can do its own echoing and backspacing in the same way for both.

The rest is translation. Incoming, telnet commands are recognised and skipped, and the line ends that different clients send are reduced to one. Outgoing, a line feed becomes carriage return and line feed, and the special command byte is doubled so it can't be mistaken for a command.

Doors, with limits

sandbox-port ' sandbox-session 16 port-door sandbox-door
admin-port ' admin-session 4 port-door admin-door
: admit  ( conn door -- )
  dup door.count @  over door.limit @ < 0= if  drop away exit  then
  1 over door.count +!
  over ['] run-session ['] spawn catch
  if  2drop  -1 swap door.count +!  drop-connection  else  drop 2drop  then ;
forth/net/repl.fs › admit
  • A door: its port, the word that runs its sessions, its limit, its count
  • Full: a task says "try again later" and closes
  • No task to be had (-275): the connection is reset
  • A listener task per door, under restarting; an app can make doors of its own

Each port is a door, made with port-door. A door holds its port number, the word that runs a session, how many sessions it allows at once, and how many it has, and the doors are kept in a list. The sandbox door allows sixteen; the admin door, four.

A listener task waits at each door. For every connection it accepts, it calls admit. If the door is full, the connection is handed to a short-lived task that tells the client to try again later, and closes. Otherwise the count goes up and a pooled task is spawned to run the session.

Spawn can fail, with -275, when every worker in the pool is busy. Admit catches that, puts the count back, and resets the connection. The listener itself carries on: a flood of connections costs connections, never the door.

Nothing here is special to the REPL. An application makes a door of its own the same way, with its own port, its own session word and its own limit, and gets the cap and the polite refusal for free. That's how the MUD serves its players.

A session's life

: (session)  ( conn run-xt -- )  swap telnet-terminal  execute ;
: tidy-session  ( i*x -- )  reset  only  false hidden !  1 sessions-served +! ;
: session  ( conn door -- )
  over >r  dup >r  'bye @ >r  door.run @
  0 eof !  ['] end-session 'bye !  0 state !  decimal
  session-idle @ io-timeout !
  ['] (session) catch ?dup if  ['] farewell catch if drop then  then
  console-terminal  0 io-timeout !  r> 'bye !
  -1 r> door.count +!  r> close-connection  tidy-session ;
forth/net/repl.fs › session
  • Set up: bye ends the session, not the system; ten minutes without input is -273
  • The terminal and the door's word, both under catch
  • However it ends: the door's place back, the connection closed, the task put back. Proven

This is a session from start to finish, and it runs in a pooled task. First, set up: keep the connection and the door on the return stack, point bye at a word that just ends the session, because bye on the console would shut the machine down, and start in decimal, not compiling. Then set the idle timeout, ten minutes. If the client goes quiet for that long, the next key it's waiting for throws -273, and the session ends.

Then, under catch, the session itself: make the connection this task's terminal, and run the door's word, which for the sandbox and admin doors sets the search order and then runs the ordinary REPL.

However it ends, by bye, by the client hanging up, by a timeout or by an error, everything is put back. The terminal goes back to the console, the door's count goes down, the connection is closed, and the stack, the state and the search order are reset. The task returns to the pool clean, ready for the next client.

Setting up the terminal used to come before the catch. It sends six bytes, and if the client had already gone, that send threw, and nothing was put back. The door kept the place taken, so sixteen such clients shut the sandbox door for good. A proof found it: it shows that whatever the session's work does, the door's place is given back and the connection closed.

What a task can see: the search order

user #order
max-order user-cells context                     \ the search order, first one first
: find-name  ( addr u -- nt | 0 )  \ in the search order
  #order @ 0 ?do
    2dup i order@ wid-latest search-list ?dup if  nip nip unloop exit  then
  loop 2drop 0 ;
forth/interpreter.fs › find-name
  • A wordlist: a chain of words of its own
  • Each task has its own search order, in its user area
  • Lookups try those wordlists, and see nothing else
  • A task whose order is the sandbox alone can reach nothing more

Lecture one described the dictionary as a single linked list. With wordlists, there can be several lists, each with its own chain of words. The full system's words are in one called forth-wordlist.

Each task has a search order: the list of wordlists to look in, first to last, kept in its user area. Find-name, which every lookup goes through, tries each wordlist in the order, and stops at the first match.

The security comes from what it doesn't do. A lookup sees only the wordlists in the order. There's no fallback to the full dictionary. So if a task's search order holds only the sandbox wordlist, then every word it can type, and every word it can compile, comes from the sandbox. Nothing else exists, as far as that task is concerned.

The sandbox

expose +      expose -      expose *      expose /      expose mod    expose /mod
…
expose dup    expose drop   expose swap   expose over   expose rot    expose nip
…
expose .      expose u.     expose .s     expose cr     expose emit   expose space
forth/sandbox.fs › expose
peer: sandbox A| 2 3 + . 5  ok
peer: sandbox A| here . here ?
peer: sandbox A| : sq dup * ; : ?
  • expose puts a word into the sandbox as a new word that calls it
  • Arithmetic, the stack, printing; no :, no @ or !, no here
  • A player-facing wordlist never reaches the full dictionary

The sandbox wordlist is built in a short file. Expose takes a word from the full system and makes a new word in the sandbox that just calls it. The list is what a stranger gets: arithmetic, logic, the stack words, and printing.

What's missing matters more. There's no colon, so no new definitions. No fetch or store, so no reading or writing memory. No here, no execute, no tick. A sandbox session can compute and print, and that's all.

The transcript from the REPL test shows it. Two plus three works. Here is unknown. And colon is unknown, so a stranger can't even define a word.

This is one of the hard rules: a player-facing wordlist must never reach the full dictionary. The MUD's player language will be built the same way, with expose, or with words written for players.

One dictionary, many tasks

: claim    ( -- )
  begin dict-owner @ dup up@ <> and while pause repeat  up@ dict-owner ! ;
: unclaim  ( -- )  dict-owner @ up@ = if 0 dict-owner ! then ;
: header   ( addr len -- )  claim header ;
: ,        ( x -- )  claim , ;
: :        ( "name" -- )  claim : ;
forth/core.fs › claim
  • Words that extend the dictionary claim it first
  • The REPL gives it up at the end of a line, unless a definition is open
  • So two admin sessions can't build definitions into each other
  • Running memory comes from reserve, never here

Every task shares one dictionary. That's fine for reading, but two tasks compiling at once would interleave their definitions, a word from one session landing in the middle of another's definition.

So the words that extend the dictionary, header, comma and colon among them, claim it first. Claim waits, pausing politely, until no other task owns it, then takes it. The REPL gives it up at the end of each line, unless a definition is still open, because a definition can span several lines with pauses in between.

That's also why memory needed while the system runs, for tasks, connections and files, comes from reserve, at the far end of the dictionary's space. A new connection's record must never be carved out of here while somebody's definition is half-built there.

Storing the admin password

  • Never the password: a slow, salted hash of it
  • Iterations measured on this machine, stored with the hash
  • SHA-256, HMAC and PBKDF2 in Forth, checked against the standards' test vectors
: hash-password  ( addr len pw -- )  \ a new salt, and the hash of the password
  >r  iterations r@ pw.iterations !
  random r@ pw.salt !  random r@ pw.salt cell+ !
  r@ pw.salt 16 r@ pw.iterations @ r> pw.hash pbkdf2 ;
forth/crypto.fs › hash-password

The admin password itself is never stored. What's stored is a hash: a fixed-size value computed from the password, from which the password can't be worked back.

It's made with PBKDF2, a standard way of making that computation deliberately slow: it runs HMAC with SHA-256 thousands of times. A fresh random salt goes in too, so that two identical passwords don't give the same hash, and precomputed tables are useless.

How many times? The first time a hash is made, the system measures how many rounds take about a quarter of a second on this machine, and uses that. The count is stored alongside the salt and the hash, so a hash made on one machine still checks on another. The whole thing is kept as a crash-safe record on the data disk.

SHA-256, HMAC and PBKDF2 are all written in Forth, with the inner block of SHA-256 in assembly as a measured hot spot. The tests check them against the published test vectors.

Logging in

: login?  ( -- flag )  \ three tries at the admin password
  3 0 do
    ." Password: " read-secret admin-pw password?  forget-secret
    if true unloop exit then
    eof @ if false unloop exit then
    2000 ms  ." Wrong password." cr
  loop false ;
forth/net/repl.fs › login?
  • Typed without echo, and wiped from memory straight after
  • Three tries, two seconds apart, then goodbye
  • No password set: port 4001 turns everyone away
  • Set it on the console: set-admin-password

On the admin door, the session's setup word asks for the password. Read-secret reads a line with echo turned off, so it never appears on the screen. Password-query hashes the guess with the stored salt and count, and compares. Then forget-secret wipes the typed password from the buffer straight away.

There are three tries, with a two-second wait after each wrong one, so guessing over the network is painfully slow, on top of the quarter second the hash itself costs. After three, the session says goodbye and closes.

Until a password has been set, the admin door turns everyone away. The first password can only be set on the console, with set-admin-password, which asks twice and stores the hash. So the first person who can reach the network never gets the full Forth by default.

Random numbers

: random  ( -- u )  \ 64 random bits
  1 drawn +!  drawn 8 random-key @ random-key cell+ @ siphash ;
forth/random.fs › random
  • At boot: a 128-bit key from the entropy HAL (virtio-rng; hosted, Linux)
  • Then random is SipHash of a counter, under that key
  • Salts, TCP sequence numbers, hash-table keys
  • Only random.fs calls entropy; everything else uses random

Security keeps needing numbers an attacker can't predict: password salts, TCP's initial sequence numbers, and the keys for hash tables that outsiders choose entries for.

They all come from one word, random. At boot, the system asks the entropy HAL for a hundred and twenty-eight bits of real randomness. On bare metal that's a virtio random number device, which QEMU feeds from the host; on the hosted build, Linux. That becomes a secret key.

After that, random is just SipHash of a counter under that key. SipHash is a keyed hash: without the key, its outputs can't be predicted, even from earlier ones. It's fast, and it's the same function used for checksums and hash tables elsewhere.

The rule is that only the random file calls the entropy HAL. Everything else asks random.

Before it faces the internet

  • Port 4001 stays on 127.0.0.1, even with its password
  • Every docs/tech-debt.md entry marked must fix before public is closed first
  • Every server sets io-timeout, and catches -275
  • New parsers get cases in the hostile test; new protocols, in the attack tests
docker run --rm -it -p 127.0.0.1:4000:4000 -p 127.0.0.1:4001:4001 -v "${PWD}:/src" os4 make run

A few rules hold the line until the system is ready for the open internet.

The admin port is published only to your own machine, with the one-two-seven address, even though it has a password. The full Forth can do anything the machine can.

The tech debt register marks some entries as must fix before public. No deployment reachable from the internet happens while any of those is open. The network REPL's own entry, which had no login and no session limits, was closed by the work in this lecture.

And two habits for new code. Any task serving a remote client sets an IO timeout and catches the pool's limit. And any new parser or protocol gets cases in the hostile test, which throws malformed input at it, and the attack test, which forges and floods.
