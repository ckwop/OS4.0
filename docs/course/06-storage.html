Storage

From a virtio disk to data that survives a crash: the block HAL, Forth's block buffers, sync, and crash-safe records.

  • The block HAL and the virtio-blk driver
  • Finding the data disk; block buffers; what sync promises
  • Records: small data that survives a crash mid-write

This lecture is about storage: how OS 4.0 keeps data on disk, and how it makes sure that data survives a crash.

We'll start at the bottom, with the block HAL, the handful of words every disk driver provides, and the virtio driver that implements them on QEMU. Then the layer every Forth system has: blocks of one kilobyte, cached in buffers, and the word sync, which is the line between a change you hope is saved and one that is.

Last, records: small pieces of binary data, like the admin password's hash, written so that a power cut in the middle of a write can never leave them half-written.

Three layers

  • Everything above the HAL is the same on every platform
  • Only blocks.fs writes, and only to the data disk

Storage comes in three layers. At the bottom is the block HAL: five words that every disk driver provides. On bare metal they're implemented by the virtio block driver; on the hosted build, by reading and writing image files through Linux.

On top of the HAL sits blocks dot fs, Forth's traditional block system, with eight buffers and the words block, update and sync. And on top of that, records dot fs, which builds crash-safe records out of pairs of blocks.

Off to the side, the file system for the app disk uses the same HAL, but only to read. That's lecture ten.

Two things follow from this shape. Everything above the HAL runs unchanged on every platform. And only one file, blocks dot fs, ever writes to a disk, and only to the data disk, which makes the hard rule about never writing the other disks easy to check.

The block HAL

\   #disks     ( -- n )             disks found
\   blk-count  ( disk -- u )        size in 1 KiB blocks; 0 if there is no such disk
\   blk-read   ( addr u disk -- )   block u into the 1 KiB at addr
\   blk-write  ( addr u disk -- )   the 1 KiB at addr to block u
\   blk-flush  ( disk -- )          make completed writes durable
hal/virtio-blk.fs
  • Disks are numbered in the order found, but never chosen by number
  • Errors throw: -33 read, -34 write, -263 a device that stops answering
  • A write is not durable until blk-flush returns

Here's the whole contract, from the top of the virtio driver. Number of disks. The size of a disk in one-kilobyte blocks. Read a block into memory. Write a block from memory. And flush.

Disks are numbered from zero in the order the driver finds them, but nothing above the HAL picks a disk by its number. That's coming up shortly.

Errors are thrown, never printed: -33 for a read that failed, -34 for a write, and -263 for a device that doesn't answer in time.

And the most important line is the last. A write that has completed may still be sitting in a cache, in the device, or in the host's memory under QEMU. Only after flush returns is it durable.

Talking to a virtio device

  • Shared memory: descriptors, and two rings
  • dmb: the ring entry before the index
  • dsb: all of it before the doorbell
  • Barriers are named Forth words, never inline
: vq-submit  ( head vq base n -- )
  2swap  dup vq-avail 2 + w@ >r                    ( base n head vq )
  r@ over vq-size 1- and 2* 4 + over vq-avail + rot swap w!
  dmb                                              \ the ring entry, then the index
  r> 1+ swap vq-avail 2 + w!
  dsb                                              \ all of it, then the doorbell
  swap vm-queue-notify vm! ;
hal/virtio.fs › vq-submit

Virtio is the standard way virtual machines talk to virtual devices, and its heart is the virtqueue: memory shared between the driver and the device.

A disk request is a chain of three descriptors. A header saying read or write, and which block. The data buffer. And a status byte that the device fills in. To submit it, the driver writes the chain's first descriptor into the available ring, advances the ring's index, and writes to a doorbell register. When the device has finished, it puts the chain in the used ring and advances that index.

Here's submit in Forth. Look at the two barrier words, dmb and dsb. The device must never see the new index before the ring entry it covers, and it mustn't hear the doorbell before both are in memory. The processor is allowed to reorder memory writes, so the barriers forbid it at exactly those two points. They're named Forth words, never inline assembly, so every ordering decision is visible in the source.

Waiting without stopping the world

: vq-wait-len  ( vq -- len )  \ and the length the device wrote
  device-timeout deadline >r
  begin dup vq-used? 0= while  r@ expired? if  r> 2drop -263 throw  then  pause  repeat
  r> drop  vq-take nip ;
hal/virtio.fs › vq-wait-len
  • Polled, not interrupt-driven: check, then pause
  • Other tasks run while the disk works
  • Five seconds without an answer: -263, not a hang

Once a request is submitted, the driver waits for the used ring to move. There are no interrupts for devices in OS 4.0, so it polls: check, and if nothing has happened, pause, letting every other task run, then check again on its next turn.

That's why a slow disk doesn't freeze the system. The task that's waiting for the disk simply keeps giving way, and the console, the network and every session carry on.

There's also a deadline. If a device doesn't answer within five seconds, the wait throws -263 rather than hanging for ever. A broken device costs one operation, not the machine.

Which disk is the data disk?

: header?  ( -- flag )  disk-header 8 s" OS40DISK" compare 0=  disk-header 8 + @ disk-version = and ;
: boot-signature?  ( -- flag )  disk-header 510 + c@ $55 =  disk-header 511 + c@ $aa = and ;
: find-data-disk  ( -- )  \ into DATA-DISK, its block 0 into DISK-HEADER
  #disks 0 ?do  disk-header 0 i blk-read  header? if i data-disk ! unloop exit then  loop
  #disks 0 ?do  disk-header 0 i blk-read  boot-signature? 0= if i data-disk ! unloop exit then  loop
  -257 throw ;
forth/blocks.fs › find-data-disk
  • First choice: a disk whose block 0 holds the OS40DISK header
  • Else: a disk that is not a FAT volume. Without a header it is read only
  • tools/blocks.py format writes the header: magic, version, volume ID, size

Several disks are attached, so which is the data disk? The answer is never its number. Cloud machines don't promise which order disks appear in, and a mistake here would mean writing over the wrong disk.

So the system looks at what's on each disk. First choice: the first disk whose block zero starts with the magic text OS40DISK and the right format version. That header is written by the formatting tool, along with a volume ID and the disk's size.

If no disk has a header, the fallback is the first disk whose block zero doesn't end in a boot signature, the two bytes that every FAT volume, including the boot disk and the app disk, has there. A disk found that way has no valid header, so it's treated as read-only. Nothing is ever written to a disk the system can't positively identify as its own.

Block buffers

  • Eight buffers: a block number, dirty, pins
  • The victim: round robin, skipping pinned ones, written back if dirty
  • block reads; buffer skips the read for a block you'll overwrite
  • Block 0, the header, can never be written: -259
: victim  ( -- i )  \ the next unpinned buffer, round robin, written back first
  #buffers 0 do
    next-buf @ 1+ #buffers mod  dup next-buf !
    dup 'pins @ 0= if  dup write-buf unloop exit  then drop
  loop -260 throw ;
forth/blocks.fs › victim

Forth's classic storage model is blocks of one kilobyte, cached in a few buffers. Here there are eight. Each buffer remembers which block it holds, whether it has been changed, which Forth calls dirty, and how many loads are reading source from it, which pins it in place.

Block asks for a block by number and returns the address of a buffer holding it. If it's already in a buffer, that's instant. If not, a victim is chosen, round robin, skipping any that are pinned. If the victim is dirty it's written back first, and then the new block is read in.

After changing a buffer, you call update, which marks it dirty, so that it'll be written back. And if you're about to overwrite a whole block, buffer gives you one without the pointless read.

One block is special. Block zero holds the disk header, and any attempt to write it throws -259.

What sync promises

: (sync)   ( -- )  (save-buffers) data-disk @ blk-flush ;
: sync           ( -- )  ['] (sync) blocks-lock locked ;  \ durable once this returns
forth/blocks.fs › sync
              -drive file=$(1),format=raw,if=none,id=data,cache=writeback \
Makefile › VIRT_CMD
  • Write every dirty buffer, then flush the device, then wait
  • update alone is a hope; sync is a promise
  • QEMU caches writes, but honours the flush; never cache=unsafe
  • New player: the record, sync; then the index entry, sync

Sync is the most important word in this lecture. It writes every dirty buffer back to the disk, then asks the device to flush, and waits until it has. When sync returns, your changes are durable: a crash or a power cut can no longer lose them.

Update on its own is only a hope. The buffer will be written back eventually, when it's chosen as a victim, but if the machine stops first, the change is gone.

The flush matters because writes are cached below us. QEMU is told to cache the data disk with write-back caching, which is fast, and it honours flush requests. The setting called cache=unsafe would ignore them, and it's banned by the hard rules.

The brief also fixes the order of writes where it matters. When a new player is created, their record is written and synced first, and only then the index entry pointing at it, synced again. A crash in between leaves an unused record, never an index pointing at nothing.

Sharing the buffers

: block   ( u -- addr )  \ block u, read from disk unless already buffered
  ['] (block) blocks-lock locked ;
: update         ( -- )  ['] (update) blocks-lock locked ;   \ the last buffer this task got
forth/blocks.fs › block, update
  • Every public word holds blocks-lock
  • A task may pause inside: waiting for the disk
  • An address from block is good only until this task next pauses
  • load pins its buffer while it reads source

All tasks share the eight buffers, and a disk request involves waiting, which means pausing. So every public word in the block layer runs holding a semaphore called blocks-lock. While one task is waiting for its block to arrive, no other task can choose the same buffer as a victim.

That gives a rule worth remembering. The address that block returns is only good until your task next pauses. After that, another task may have reused the buffer for a different block. So read it, change it, and call update, without anything that pauses in between. Update also works on the last buffer your own task asked for, so another task's request can't confuse it.

Load is the exception that needs more: it interprets source straight out of a buffer, and that can take many pauses. So load pins its buffer, and the victim search skips it.

Records: surviving a crash mid-write

0
1 cells field r.check           \ SipHash of everything after it, up to the data's end
1 cells field r.seq             \ 1 for the first write; 0 means never written
1 cells field r.len
0 field r.data
constant /record-header

Some data is small but precious, like the admin password's hash. If the machine loses power while a block is being written, the block can end up half old and half new, which is called a torn write. A record is built so that can never matter.

A record uses two blocks, and keeps two copies. Each copy holds a checksum, a sequence number, the length, and the data. Writes alternate: each new write goes over the older of the two copies, with the next sequence number.

Reading checks both copies and takes the newest one whose checksum is right. So if a crash tears the write in progress, as in the picture, that copy fails its checksum, and the reader quietly takes the previous one. You get either the new value or the old one, never a mixture.

The checksum is SipHash, keyed with a fixed key: here it's not protecting a secret, just detecting damage.

Writing a record

: (record!)  ( addr len n -- )
  over /record u> if -274 throw then
  dup copy-seq  over 1+ copy-seq                   ( addr len n s0 s1 )
  2dup max 1+ >r  u< 0= if 1+ then  r> swap         \ the next number, over the older copy
  ['] fill-copy blocks-lock locked
  sync ;
forth/records.fs › (record!)
  • Up to 1000 bytes of binary data: never Forth source, never execution tokens
  • Synced before record! returns
  • Used for the admin password's hash, in blocks 998 and 999

Here's the write. Refuse anything too large for one block. Read both copies' sequence numbers; an invalid copy counts as zero. The next number is one more than the larger, and it goes over the older copy. Fill that buffer while holding the block lock, so no other task can take the buffer in between. And sync, so that when record-store returns, the new value is durable.

Records hold up to a thousand bytes of binary data. Two hard rules apply to all stored data, and records are where they bite. Never store data as Forth source, which something might later interpret. And never store execution tokens: they're memory addresses, and they change every time the system is rebuilt.

The network REPL keeps the admin password's hash in a record, in blocks nine nine eight and nine nine nine.

Try it on the console

.disk                                  \ volume ID and size
5 wipe                                 \ blank block 5 and edit it
0 >line \ my first screen
1 >line : hello ." Hello from block 5" ;
5 list                                 \ show it
sync                                   \ durable now
5 load hello                           \ compile it, run the word it defined

With -v "${PWD}:/src" and make run, the data disk is build/data.img, kept between runs. python3 tools/blocks.py list build/data.img 5 shows the screen from the host.

To try it, boot with your working copy mounted, so the data disk is kept between runs. Dot-disk shows the volume ID and size.

Wipe blanks block five and makes it the current screen. To-line replaces one of its sixteen lines; line zero is, by convention, a comment saying what the block holds. List shows it. Sync makes it durable. And load compiles it, after which hello is a word you can run.

Shut down, boot again, and block five is still there. The blocks tool can list it from the host too.
