When things go wrong

One mechanism for every error, from a typo to a bad memory access: throw a code, catch it further up.

  • catch and throw, and how the REPL survives every line
  • Errors the kernel finds: stacks, division, undefined words
  • Faults the processor finds, and where an error happened

This lecture is about errors, and the good news is that there's only one mechanism to learn. Whatever goes wrong, whether it's a mistyped word, a division by zero, a stack overflow, or the processor itself refusing a bad memory access, the result is the same: a number is thrown, and something further up catches it.

We'll look at catch and throw themselves, and at how the REPL uses them so that no single line can bring the system down.

Then the errors the kernel detects in assembly, the faults the processor detects, and how the system reports not just what went wrong, but where.

Throw a number, catch it further up

  • xt catch runs xt; returns 0, or the code thrown
  • n throw unwinds to the innermost catch; 0 throw does nothing
  • The data stack's depth is put back as it was at catch

Catch takes an execution token and runs it. If it finishes normally, catch leaves a zero. If anything inside it, however deeply nested, throws a number, the throw comes straight back out of catch, which leaves that number instead.

Each catch leaves a frame on the return stack, and a user variable called handler points at the innermost one. Here the REPL has a frame round the current line, and inside it, a word called safe-div has a frame of its own round a division. When the division throws -10, throw jumps straight to safe-div's frame. Nothing in between runs any further.

Zero throw does nothing at all, which is convenient: you can pass a result code straight to throw without testing it first.

And when a throw arrives, the data stack is put back to the depth it had when catch started, so the catcher knows exactly what's on it.

Six lines of Forth

: catch  ( i*x xt -- j*x 0 | i*x n )
  sp@ >r  handler @ >r  rp@ handler !
  execute
  r> handler !  r> drop  0 ;
: throw  ( k*x n -- k*x | i*x n )
  ?dup if
    handler @ 0= if abort then   \ nothing to catch it: the kernel's ABORT
    handler @ rp!  r> handler !  r> swap >r  sp! drop  r>
  then ;
forth/core.fs › catch, throw
  • catch: save the stack pointer and the old handler; this frame is the handler now
  • throw: return stack back to the frame, restore the handler, then the data stack
  • Returning from throw returns from catch, with the code

Here they are, and they're short. Catch saves the data stack pointer on the return stack, then the current handler, then makes this frame the handler. It executes the token. If that returns normally, catch takes its frame off and leaves zero.

Throw, with a non-zero code, first checks there's a handler at all. If not, it falls back to the kernel's abort. Otherwise it sets the return stack pointer to the frame, which instantly discards every call in between. It restores the outer handler, puts the data stack pointer back, and leaves the code.

Here's the clever part. Throw now returns, and because the return stack was reset to catch's frame, it returns to wherever catch was going to return to. So the code appears as catch's result, exactly as if catch had finished normally. There's no special unwinding machinery: just two stack pointers being put back.

The REPL catches every line

: repl  ( -- )  \ until the end of input
  unclaim
  begin refill while
    ['] interpret catch ?dup if .error reset else prompt then
    state @ 0= if unclaim then
  repeat reset ;

-99 throw error -99

tests/exceptions.out
  • Each line runs under catch
  • .error prints the message; reset empties the stack and stops compiling
  • Every task's REPL does the same: a telnet session too

Now the REPL. Each line you type is interpreted under catch. If the line throws, dot-error prints a message for the code, and reset empties the data stack, stops any half-finished definition, and gives up the dictionary.

Here are three lines from the exceptions test. Dividing by zero prints division by zero. Throwing a code with no message of its own prints error and the number. And a word that throws and isn't caught anywhere inside is caught by the REPL in just the same way.

So no single line can stop the system. You lose that line, and you're back at the prompt. Every task that interprets, including each telnet session, runs this same loop with its own handler and its own stacks, so one session's mistake never touches another.

Codes and their messages

: message:  ( n "text" -- )  \ the rest of the line is the message
  align here  messages @ ,  messages !  ,
  0 parse  dup ,  here swap dup allot cmove  align ;
forth/output.fs › message:
-262 message: stopped by the watchdog: it ran too long without pausing
-273 message: timed out
  • Standard codes: -4 underflow, -10 division by zero, -13 undefined…
  • The system's own from -256 down, each file registering its own
  • New error conditions throw a code; they never print and abort

Error codes come from the Forth standard where one fits. Minus four is stack underflow, minus ten is division by zero, minus thirteen is an undefined word, and so on.

The system's own codes count down from -256. Each file registers text for the codes it throws, with message-colon, which simply adds an entry to a linked list: the code, and the rest of the line as its text. The tasks file registers the watchdog's message; the TCP file registers timed out.

That leads to a rule for new code. A new kind of error throws a code, and registers a message for it if it needs one. It never prints something and gives up on its own. That way the caller always gets to decide: report it, retry, or turn one client away while serving the rest.

arch/aarch64/outer.s › try_throw
  • Primitives find errors too: division by zero, overflow, a missing name
  • try_throw calls the Forth throw, as if the word had
  • It resets both stacks to the frame first: they may be the problem

Some errors are found in assembly. The division primitive checks for zero. The compiler checks names. And the stack checks, which we'll see next, are in the kernel too.

They all end up in a routine called try throw, which hands the code to the Forth throw, as if the word that failed had called throw itself. The kernel learns where the Forth throw is when core dot fs stores its execution token in a kernel variable.

There's one subtlety. Before calling throw, it resets both stack pointers to the catch frame, doing by hand what throw would do. Why? Because the error might be that a stack has overflowed. Throw is a Forth word that uses the stacks, and it mustn't trip over the very problem it's reporting.

Stack limits

.macro CHECK_STACKS
	ldp	x9, x10, [UP, #U_SLIMIT]
	cmp	DSP, x9
	b.lo	err_overflow
	cmp	RSP, x10
	b.lo	err_roverflow
.endm
arch/aarch64/kernel.s › CHECK_STACKS
deep return stack overflow
pusher stack overflow
  • Checked in every colon call, branch, loop and pause
  • So runaway recursion and runaway loops are caught
  • The limit leaves 16 cells of room: enough to report the error
  • Underflow is checked after each word at the prompt

Each task's stacks are only two kilobytes, and they sit right next to its user area. A runaway recursion that simply kept going would overwrite the task's own variables, and then anything could happen.

So the kernel checks. Every time a colon word is called, every backward branch, every loop and every pause runs this macro: two loads and two comparisons against limits stored in the user area. Those are exactly the places where a stack can grow without end.

The two lines from the limits test show it working. A word that calls itself for ever gets return stack overflow. A loop that pushes for ever gets stack overflow. Both come back to the prompt.

The limit is set sixteen cells short of the real end, so there's room left to report the error. Underflow, taking more than is there, is cheaper to check after each word at the prompt, and that's what the interpreter does.

  • Then return from the exception into exception_throw
  • It throws -256, caught like any other error
  • Hosted: a signal, the same report and the same throw

Some errors only the processor can see. Reading from an address where there's no memory is the classic case. Here the test reads from a made-up address, and the processor raises a synchronous exception.

The exception handler prints a register dump: the kind of exception, the syndrome register, which encodes why, the address of the instruction, the address that was accessed, and all the registers. The test's filter masks the registers, which change from build to build.

Then comes the trick. Instead of returning to the faulting instruction, the handler changes the return address to exception throw, and returns there. That routine throws -256, which is caught like any other error. The REPL prints nothing more, because the dump has said it all, and you're back at the prompt.

On the hosted build, Linux reports the fault as a signal. The handler prints a shorter report and makes the same throw, so the same test passes on both.

Saying where

: .error  ( n -- )
  dup -1 = over -256 = or if drop exit then   \ ABORT; a CPU fault has its own report
  .where
  dup -2 = if drop abort-msg 2@ type cr exit then
  dup -13 = if drop errname 2@ type ."  ?" cr exit then
  dup -14 = if drop errname 2@ type ."  is compile-only" cr exit then
  dup message if type cr drop exit then
  ." error " (.) type cr ;
forth/errors.fs › .error
  • .where: app.fs:12: for a file, block 20 line 3: for a block
  • The boot files: forth/tasks.fs:40:, then the system stops
  • An undefined word names itself: nosuchword ?

A good error report says where, as well as what. Dot-error is the one place reports are printed. It ignores abort and processor faults, which have reported themselves. Then dot-where prints the location, if the error happened while loading source rather than at the prompt.

For a file on the app disk, that's the file name and line number, like a compiler would print. For a block of Forth source on the data disk, it's the block and the line within it. Both are tracked as the source is loaded, and noted at the moment of the error, by the innermost file or block, before the stacks unwind.

The boot files get the same treatment from the kernel, as you saw in lecture three, except that an error there stops the system.

Finally, a few codes have special reports. An undefined word prints the word itself, followed by a question mark, which is the traditional Forth way of saying I don't know that.

Errors in tasks

: report  ( n -- )  task-name 2@ type ." : " .error ;
: run-task  ( i*x xt -- )  \ a task's whole life: run xt, report how it ended, sleep
  catch ?dup if  ['] report catch if drop then  then   \ its terminal may be gone
forth/tasks.fs › report, run-task
  • A task's work runs under catch: the report names the task
  • Even the report is caught: a session's terminal may have gone
  • System loops restart; per-item catch keeps a fault to one item
  • The watchdog's -262 is just another throw

Tasks use the same mechanism. Every task's work runs under catch, in run-task. If it throws, report prints the task's name and the error, so you can tell which task failed.

Notice that the report is itself under catch. A telnet session's terminal is its network connection, and if the error was that the connection closed, printing the report would fail too. That second error is quietly dropped.

The tasks lecture covered the rest. System loops run under a word called restarting, and catch per item inside, so a bad packet costs one packet. And the watchdog's error, -262, is just another throw, landing in whichever task wouldn't pause.

One mechanism, used everywhere: that's what makes the system hard to knock over.

Try it on the console

1 0 /                              \ division by zero
: risky  ( n -- )  dup 0= if -42 throw then . ;
5 ' risky catch .                  \ 5 0
0 ' risky catch . .                \ -42 0
: deep  ( -- )  recurse ;
deep                               \ return stack overflow
$123456789000 @                    \ a register dump, then ok
nosuchword                         \ nosuchword ?

Try these at the console. Divide by zero. Define risky, which throws -42 when given zero, and catch it: with five it prints five and returns zero, with zero it leaves the code and the untouched input.

Then recurse for ever, and see the return stack overflow caught. Read from a made-up address and watch the register dump, followed by the prompt. And type a word that doesn't exist. After each one, the system is exactly as it was.

Questions to think about…

  1. After 0 ' risky catch, the stack holds 0 -42. Where did the 0 come from, and why must catch restore the depth?
  2. Why does try_throw reset the stacks itself instead of leaving it to throw? Construct the failure it prevents.
  3. A word you are writing finds a corrupt record. Should it print a warning, return a flag, or throw? What does each choice cost its callers?

That's errors. Throw a number, catch it further up; the REPL catches every line; the kernel and the processor feed their errors into the same throw; and reports say what and where.
