The map

What OS 4.0 is, how the repository is laid out, and how it is built and tested. The rest of the course fills in each area.

We'll see what the system is and what it's for, how one kernel is built two ways, and the three disks it uses.

A Forth operating system

  • No Linux underneath: it owns the machine
  • Most of it is Forth, even the drivers
  • Built to run a MUD, kept general for other apps

OS 4.0 is a small operating system written in Forth for 64-bit ARM processors. Here are its layers, from the bottom up.

At the bottom is the machine. Today that's QEMU's virtual ARM board, called virt. Later it will be an AWS Graviton server. There's no Linux underneath and no other operating system: OS 4.0 owns the machine, from the first instruction.

Above it is a small kernel in assembly language. It holds the Forth primitives, a minimal compiler, and the start-up code. Everything else is Forth, loaded at boot from the files in the forth and HAL folders: the rest of the language, the device drivers, multitasking, disk blocks, a network stack, and the interactive prompt, which Forth calls the REPL.

On top runs an application. The first will be a MUD, a text adventure that many people play at once over the network. But the base is kept general, so that other applications can run on it too.

One kernel, two builds

  • The same Forth on both: only the drivers differ
  • The platform supplies hal_key, hal_emit, hal_bye…
  • Every test runs on both builds
.ifdef HOSTED
	bootfile "hal/linux-blk.fs"
	…
.else
	bootfile "hal/virtio.fs"
	…
.endif
arch/aarch64/kernel.s › boot_files

The kernel is one assembly file, kernel dot s, which pulls in the rest of the assembly and embeds the Forth boot files. It's assembled twice, once for each platform.

The hosted build links it with linux dot s and runs it as an ordinary Linux program, under a small emulator called qemu-aarch64. It starts in a blink, which makes it ideal for quick tests. The bare-metal build links it with virt dot s instead and boots on QEMU's virtual machine, through a boot loader called Limine. The Forth on top is the same: only a handful of tiny routines, for reading a key, printing a character, and shutting down, come from the platform. And a few drivers differ, which the conditional block here chooses.

Because the two builds share everything else, every test runs on both. When they agree, you can trust that the Forth is right and the platform code is right.

Where things live

  • docs/brief.md: the specification
  • DECISIONS.md: every open choice, with its reason
  • docs/tech-debt.md: shortcuts, gaps and risks
  • CLAUDE.md: the conventions, in brief

Here's the repository. The four folders marked in orange are the operating system itself. Arch slash aarch64 holds the assembly. Forth holds the language and the system services, with the network stack in its own sub-folder. And hal, the hardware abstraction layer, holds the drivers, also written in Forth.

Tools holds the Python helpers that build disks and run tests, tests holds the tests, docs holds the documentation including this course, and examples holds a small example application.

Four documents explain the why. The brief is the specification: read it first. Decisions records every choice the brief left open, with a one-line reason, numbered so that code comments can point at them. Tech debt lists shortcuts and known gaps, and some are marked must fix before the system goes public. And the CLAUDE file gathers the conventions in one place.

The boot files, in order

	bootfile "forth/core.fs"
	bootfile "forth/output.fs"
	…  drivers from hal/
	bootfile "forth/blocks.fs"
	bootfile "forth/errors.fs"
	bootfile "forth/tasks.fs"
	bootfile "forth/random.fs"
	bootfile "forth/crypto.fs"
	bootfile "forth/records.fs"
	bootfile "forth/net/eth.fs"
	…  arp, ip, icmp, udp, tcp, telnet, net
	bootfile "forth/interpreter.fs"
	bootfile "forth/sandbox.fs"
	bootfile "forth/files.fs"
	bootfile "forth/net/repl.fs"
	bootfile "forth/app.fs"
	bootfile "forth/start.fs"	// last: starts the Forth QUIT loop
arch/aarch64/kernel.s
  • Each file builds on the ones before it
  • Compiled from source at every boot: under a second
  • An error while loading prints file:line: and stops

This list in the kernel is the order in which the system builds itself. Each line embeds one Forth source file in the kernel image.

Core comes first and finishes the language. Output adds printing and strings. Then come the drivers for the platform, then blocks, error reporting, tasks, random numbers and cryptography, crash-safe records, and the network stack, layer by layer. Then the interpreter, the sandbox, the app disk's files, the network REPL and app start-up. Each file uses only words defined by the files above it.

All of this is compiled from source at every boot, by the small interpreter in the kernel. It takes well under a second. There's no separate build step for the Forth, and nothing precompiled to drift out of date.

If a boot file has a mistake, the kernel prints the file name and line number, and stops. You'll see that mechanism again in the lecture on booting.

Three disks, three jobs

  • A hard rule: the OS never writes the boot disk or the app disk
  • FAT for what the OS only reads; blocks for what it writes

The system runs with three disks, each with one job.

The boot disk holds the boot loader and the kernel. The data disk is a plain array of one-kilobyte blocks, with a header in block zero, and it's the only disk the system ever writes. And the app disk holds the application's source files. It's formatted as FAT, the same file system as a USB stick, so it can be made with ordinary tools.

That split is one of the hard rules. The operating system never writes to the boot disk or the app disk. FAT is used for what the system only reads, because standard tools can build it; blocks are used for what it writes, because they're simple enough to make crash safe.

Notice the line at the bottom. The system tells the disks apart by looking at what's on them, never by the order they happen to be attached in. Cloud machines don't promise an order.

Everything builds in Docker

# once: the toolchain image, the kernel and the boot disk
docker build -t os4 .

# boot to the Forth prompt on the serial console
docker run --rm -it os4

# the test suites, against your working copy
docker run --rm -v "${PWD}:/src" os4 make test
  • Nothing is installed on the host but Docker
  • The image holds cross binutils, QEMU, Limine, gforth and Python
  • Make targets: build image run run-hosted test test-hosted test-virt

The host machine has no tools of its own: no assembler, no QEMU, no make. Everything happens inside a Docker image.

Building the image fetches the cross assembler for ARM, QEMU, the Limine boot loader, gforth, which is a standard Forth used to check results, and Python for the tools. It also builds the kernel and the boot disk, so the second command boots the system straight away.

For day-to-day work, you mount your working copy into the container and run make targets against it. Make test runs the whole suite. There are targets to build, to make the boot image, to boot either build, and to run the tests on one build only.

tests/stack.out: what must come back
  • Byte for byte, on both builds
  • Every feature adds tests; the whole suite runs on every change

Every test is a transcript. The dot in file is typed at the console, line by line, exactly as a person would.

The dot out file is what must come back: the banner, then each line as the system echoes it, its output, and ok. The values are checked by hand, and against gforth for standard words, before a transcript is committed.

The output must match byte for byte, on both builds. It's a blunt instrument, and that's its strength: any change in behaviour, however small, shows up as a difference. Every feature adds tests, and the whole suite runs on every change. The last lecture shows the test tools in detail.

The rules that shape it

  • Forth first. Assembly only for primitives, the thinnest hardware access, start-up and measured hot spots
  • Hardware through the HAL. key emit blk-read blk-write net-send net-poll: no driver details above hal/
  • Durable means synced. sync writes the buffers, flushes the device and waits
  • Strangers get a sandbox. A player-facing wordlist never reaches the full dictionary
  • Data is data. Never store player data as Forth source; never persist execution tokens

A few rules run through the whole system, and knowing them makes the code easier to read.

Forth first. Assembly is used only where it must be: the primitives, the thinnest layer of hardware access, start-up, and places where measurement showed Forth was too slow. Even then, the Forth version is kept as the reference.

Hardware goes through the HAL. Everything above the drivers uses a few words like key, emit, block read and block write, network send and network poll, so the same code runs on QEMU, on Linux, and later on real cloud hardware.

Durable means synced. A change is only safe once sync has written the buffers, flushed the device, and waited for it to finish.

Strangers get a sandbox. Anyone connecting over the network sees a small wordlist that cannot reach the rest of the system.

And data is data. Player data is never stored as Forth source to be run later, and execution tokens, which are memory addresses, are never written to disk.
