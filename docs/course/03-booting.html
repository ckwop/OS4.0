Booting

From power on to the ok prompt: firmware, Limine, a little assembly, and then the system compiling itself.

  • The boot disk, Limine, and the higher half
  • Memory, devices and the timer
  • The bootstrap interpreter, and handing over to Forth

This lecture follows the machine from the moment it's switched on to the moment you see ok. It takes about ten seconds under QEMU, and most of that is the firmware.

We'll look at the boot disk and the boot loader, Limine, and why the kernel lives at the very top of the address space. Then the few things the kernel must set up for itself: memory for the dictionary, access to devices, and a timer.

And finally the most Forth-like part: a tiny interpreter in assembly that compiles the boot files, and then hands the keyboard over to the real interpreter, written in Forth.

The journey

  • Firmware and Limine find the kernel on the boot disk and load it
  • Two short stretches of assembly set up the machine and the Forth
  • From there on, Forth builds the rest of the system

Here's the whole journey in one line. The first two steps aren't ours. QEMU starts its UEFI firmware, the same kind of firmware a PC has. The firmware finds the boot loader, Limine, on the boot disk and runs it. Limine reads its configuration, loads our kernel into memory, and jumps to it.

Then come two short stretches of assembly. Underscore start, in virt dot s, sets up the machine: exceptions, devices, the console, the timer and memory. Then forth cold, in outer dot s, sets up the Forth machine and starts compiling the boot files.

From there, everything is Forth. The boot files are compiled one by one, and the last of them starts the application, or the network REPL, and then the interactive prompt on the console.

The boot disk is made by this rule in the Makefile, with ordinary tools. Make a sixty-four megabyte file, format it as FAT, and copy three things onto it.

First, Limine itself, as BOOTAA64.EFI in the folder E F I slash boot. That's the place UEFI firmware looks for the boot loader of a removable disk on an ARM machine, so no firmware settings are needed. Second, Limine's configuration, shown on the right: no menu, no delay, one entry, which loads the kernel using Limine's own protocol. And third, the kernel itself.

QEMU attaches this disk read-only. The operating system never writes to it, and that also lets every test share one copy.

Into the higher half

{
    . = 0xffffffff80000000;
arch/aarch64/virt.ld
  • Limine's protocol requires a higher-half kernel
  • The dictionary: the largest usable region in Limine's memory map
  • Capped at 128 MiB, for the code fields' reach

Limine's protocol expects the kernel in the higher half: the top two gigabytes of the sixty-four-bit address space. The linker script puts it there, starting at this address, as one segment that's readable, writable and executable.

Limine also leaves the MMU on, with page tables of its own. They map the kernel, and all of RAM in a second place called the direct map.

The kernel asks Limine two questions through request blocks in its data section: the memory map, and where the direct map starts. It picks the largest usable region of RAM, reached through the direct map, and that becomes the Forth dictionary. Lecture two explained the cap: it's limited to a hundred and twenty-eight megabytes so that code fields can reach the trampolines.

What Limine doesn't map is the devices. That's the next job.

_start: setting up the machine

_start:
	mov	x0, sp				// run on SP_EL1, keeping Limine's stack,
	msr	spsel, #1			// so exceptions and the kernel share one
	mov	sp, x0
	ldr	x0, =vectors
	msr	vbar_el1, x0
	isb
	bl	map_devices
	bl	uart_init
	bl	timer_init
	… check that Limine accepted base revision 3
1:	bl	find_memory
	cbnz	x1, forth_cold
arch/aarch64/virt.s › _start
  • Exception vectors first: a fault from here on is reported
  • Devices, the serial port, the timer
  • Then the dictionary's memory, and into the Forth kernel

This is underscore start, the first of our code to run. It's short enough to read in one go.

The first three lines choose which stack pointer the processor uses, keeping the stack Limine gave us. Then the exception vectors are installed: the table of handlers the processor jumps to on an interrupt or a fault. Doing this first means that any fault from here on prints a report, instead of hanging silently.

Then three subroutines. Map the devices into the address space, make sure the serial port is on, and start the ten-millisecond timer.

After checking that Limine understood which version of its protocol we asked for, find memory picks the region for the dictionary, and, if it found one, the code branches into forth cold, in the portable kernel. The platform part of booting is done.

Mapping the devices

  • Two page tables and one 1 GiB block: virtual = physical
  • Device memory: no caching, no reordering, never executed
  • TTBR0 covers the low half, which Limine leaves to us
	// 1 GiB block at physical 0: Device memory, access flag set, never executable
	.equ	PTE_DEVICE_BLOCK, (1 << 54) | (1 << 53) | (1 << 10) | (MAIR_IDX_DEVICE << 2) | 0x1
arch/aarch64/virt.s › map_devices

On QEMU's virt board, every device sits in the first gigabyte of physical addresses: the serial port, the interrupt controller, and thirty-two slots for virtio devices, which is where the disks, the network card and the entropy source appear.

The kernel maps that whole gigabyte with just two small page tables. The level zero table points to a level one table, whose first entry maps one gigabyte block, so that each virtual address equals the physical address. An address you read in a device's data sheet works as it is.

The entry's bits mark it as Device memory. That matters: device registers must not be cached, and reads and writes to them must not be reordered or merged, or the device would see nonsense. The never-execute bits stop the processor from ever fetching instructions there.

The table goes in the register TTBR0, which handles the lower half of the address space. Limine only uses the upper half, so the two don't collide.

The timer tick

1:	ldr	x0, =tick_period		// the tick
	ldr	x0, [x0]
	msr	cntv_tval_el0, x0
	mrs	x0, elr_el1
	str	w9, [sp, #-16]!
	bl	watchdog_sub
	ldr	w9, [sp], #16
	cbz	x0, 8f
	msr	elr_el1, x0			// resume the running task in watchdog_throw
arch/aarch64/virt.s › hal_irq
  • The virtual timer interrupts every 10 ms, through the GIC
  • Each tick: re-arm the timer, then ask the watchdog
  • The only interrupt: devices are polled
  • An idle CPU waits in wfi until the next tick

Timer init programmed the processor's virtual timer to interrupt a hundred times a second, routed through the interrupt controller, the GIC.

This is what happens on each tick. Set the timer for the next one. Then call the watchdog, passing the address the interrupted code was about to run. If the running task has gone too long without pausing, the watchdog returns a different address, and the interrupt returns there instead, so the task throws an error. You saw the watchdog in lecture five.

The tick is the only interrupt the system uses. Disks, the network and the console are all polled: a task asks whether there's anything new, and pauses if not. That keeps the code simple, with no interrupt handlers racing the tasks.

And when no task has anything to do, the processor waits for an interrupt, so an idle machine sleeps until the next tick.

arch/aarch64/outer.s › forth_cold
  • The trampolines first, then the dictionary after them
  • The console becomes task zero: a ring of one
  • The first line of the first boot file is the input

Forth cold is where the portable kernel takes over. It's given the dictionary's address and size, and the same code runs on both builds.

It first writes the four trampolines from lecture two at the start of the dictionary, and starts the dictionary proper just after them.

Then it makes the console into a task. The user area pointer is set to a block of memory reserved for it, and its link points to itself, so the ring of tasks has exactly one member. Its stacks, their limits, its name and its number base are filled in, which is the part elided here.

Last, it points the input at the first line of the first boot file, and jumps into the interpreter loop. From now on the system is reading Forth, just as if someone were typing it very fast.

The bootstrap interpreter

interpret:
	…
	bl	parse_name_sub
	cbz	x1, 5f
	mov	x24, x0
	mov	x25, x1
	bl	find_sub
	cbz	x0, 2f
	ldr	x2, [UP, #U_STATE]
	cbz	x2, 1f			// interpreting
	cmp	x1, #1
	b.eq	1f			// immediate
	bl	comma_sub
	NEXT
1:	mov	x8, x0
	br	x8
arch/aarch64/outer.s › interpret
  • The same logic as the Forth interpret, in assembly
  • Numbers in 2:; the end of a line refills from the next
  • Only for the boot files: an error prints file:line: and stops

To compile the first boot file, the kernel needs an interpreter before any Forth exists. So it has a small one in assembly. Compare it with the Forth interpret from lecture one: it's the same logic.

Parse the next word. If the line is empty, go and get the next line. Look the word up. If it's found, and the system is compiling, and the word isn't immediate, compile it with comma. Otherwise jump straight to it. After label two, not shown, a word that isn't found is tried as a number.

Its input comes from the embedded files, a line at a time, moving on to the next file at the end of each. It's only used for the boot files. An error here is fatal: it prints the file name, the line number and the message, and the system stops, because a half-built system isn't worth running.

' (quit) 'quit !

forth/start.fs
  • The interpreter file stores the Forth REPL in 'quit
  • start.fs prints the banner, starts the app, and calls quit
  • quit now runs the Forth loop: the assembly one is never used again

How does the assembly interpreter hand over? Through one variable. Near the end of the interpreter file, the Forth REPL is defined, and its execution token is stored in a kernel variable called tick-quit.

Start dot fs is the last boot file, and it's three lines. Print the banner, start the application or the network REPL, and call quit.

Quit resets the return stack and looks at tick-quit. Now that it's set, quit switches the input from the boot files to the terminal and runs the Forth loop. The assembly interpreter is never used again. Everything you type is read by the REPL written in Forth, which means it can be changed and extended in Forth, like the rest of the system.

Quit also runs after an error that nothing caught. Only the console gets a fresh REPL then. Any other task has lost its place, so it retires instead, which you'll meet in the lecture on tasks.

The hosted build: the same boot, on Linux

1:	mov	x28, x0
	bl	terminal_raw
	bl	faults_init
	bl	timer_init
	mov	x0, x28
	ldr	x1, =DICT_BYTES
	b	forth_cold
arch/aarch64/linux.s › _start
  • The dictionary: 128 MiB from mmap, readable, writable, executable
  • The terminal in raw mode: Forth does its own echo
  • Faults arrive as signals: reported and thrown as on bare metal
  • The tick is SIGALRM, every 10 ms

The hosted build boots the same way, with Linux standing in for the hardware. Its underscore start asks Linux for a hundred and twenty-eight megabytes of memory that can be written and executed, for the dictionary.

It puts the terminal in raw mode, so that keys arrive one at a time and the Forth does its own echoing, just as on the serial console. It catches faults, which Linux delivers as signals, so that a bad memory access is reported and thrown, as on bare metal. And it asks for an alarm signal every ten milliseconds, which stands in for the timer interrupt and drives the same watchdog.

Then it branches to the same forth cold, with the memory's address and size. From that point the two builds run identical code.

Questions to think about…

  1. Why install the exception vectors before mapping the devices? What would you see if the order were reversed and the mapping faulted?
  2. Device memory forbids caching and reordering. Which bug would you expect if the devices were mapped as normal memory?
  3. An error in a boot file stops the system. An error typed at the prompt doesn't. Why is each the right choice?

That's booting. The firmware and Limine load the kernel, a little assembly sets up the machine and the Forth machine, the bootstrap interpreter compiles the boot files, and the Forth REPL takes over.

Three questions to think about: the order of the first steps, why devices need their own kind of memory, and why errors at boot and errors at the prompt are treated so differently. That last one leads straight into lecture four: when things go wrong.
