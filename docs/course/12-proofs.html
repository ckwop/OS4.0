Proofs

Lean 4 theorems about the dictionary as the system compiles it: how the words get into Lean, the three kinds of proof the generator writes for every word, the ones written by hand, and how to run and read them.

  • From Forth to Lean: the dump, the generator, the model
  • Certificates and bridges: stack effects, step counts, footprints
  • Proofs by hand, running them, and what is still trusted

The tests from the last lecture try some inputs, and check what comes back. This lecture is about the other half of being sure: proofs, which cover every input at once.

The proofs are written in Lean, a language for stating theorems and checking their proofs by machine. We'll see how the Forth words get into Lean, from the dictionary as compiled, and the model of the machine they run on. Then the three kinds of proof the generator writes for every word it can: stack effects, step counts between pauses, and footprints, which say what a word may write.

Then the proofs written by hand, how to run them all, what to do when one fails, and what is still taken on trust.

About the code as compiled

proofs-extract: $(GENERATED)

proofs: proofs-extract
	cd proofs && lake build
Makefile › proofs

The proofs are about the system as it is compiled, never about a copy of it. Make proofs boots the hosted build, which loads every boot file. A small Forth program then prints the whole dictionary, word by word, as it ended up in memory. A Python generator turns that into Lean definitions, one per word, and the theorems about them. Lake, Lean's build tool, checks the lot, beside a model of the machine and the theorems written by hand.

Why the dictionary and not the source? A copy written by hand goes stale without anyone noticing. Proofs about what the compiler produced change when the Forth does, and fail the build when a property stops holding. And by the time a word is in the dictionary, the immediate words, if, do, and the rest, have done their work, so there is no second compiler to trust. When the spike that started this tried a bug on purpose, an unsigned comparison made signed, all thirty-six hosted tests passed. Its proof failed.

The dump

\ Each word is one line, numbers in decimal: "@@ xt kind name cells...", where
\ kind is 0 primitive, 1 colon, 2 constant, 3 variable, 4 other (a DOES> child).
…
  cr ." @@ top " dict-top u.                       \ where reserved memory ends
  here limit !  latest @ begin ?dup while  dup .word  dup limit !  @ pause repeat
tools/dump-words.fs › dump-words
  • One line per word: its xt, its kind, its name, its raw cells
  • A body ends where the next newer header starts: the Forth decodes nothing
  • @@ top: where reserved memory ends
  • Kept until the hosted build changes

The dumper is forty lines of Forth, fed to the hosted build's console. It walks the dictionary from the newest word to the oldest, and prints one line for each: its execution token, its kind, its name, and then its cells as plain numbers. Kind zero is a primitive, one a colon word, then constants, variables, and children of defining words.

It doesn't decode anything. A word's body simply runs until the next header, so the dump is the raw memory, and all the interpretation happens in one place, in the generator.

The first line gives the top of the dictionary's space, since memory taken by reserve sits just below it. The dump only changes when the build does, so it's kept between runs.

Threads become instruction lists

: +!      ( n addr -- )  dup @ rot + swap ! ;
forth/core.fs › +!
@[forth] noncomputable def «+!».code : List Ins := [.call Prim.dup, .call Prim.fetch, .call «rot»,
  .call Prim.plus, .call Prim.swap, .call Prim.store, .exit]
noncomputable def «+!» : Sem := thread «+!».code
proofs/OS4/Words/Core.lean, generated (wrapped here)
  • Each cell decoded: a call, a literal, a branch, a loop instruction, or exit
  • Forward branches only: thread. Loops: loopThread
  • Callees are defined first; each word's Lean follows its Forth

Here's a small word, +!, which adds a number to the cell at an address. Below it is what the generator wrote for it. Each cell of the thread has become one instruction: a call to the duplicate primitive, a call to fetch, a call to the colon word rot, and so on, then exit. The word itself is that list, run by the model's thread interpreter.

The generator recognises the few cells that aren't calls: a literal and its value, the two branches with their targets, the instructions of do loops, and exit. Branch targets become positions in the list.

A word whose branches all go forwards runs each instruction at most once, so it's an ordinary thread. A word with a loop is a loop thread, whose meaning is its result if it ends. Callees are always defined before their callers, so every word in Lean is built from words already there.

what the generator reported when this lecture was written
  • Addresses are named, never their values: the same Lean every boot
  • A module per boot file: Words/Core.lean, Words/NetTcp.lean; only what changed is re-proven
  • Left out: words the model can't express, with the reason

The dictionary lands at a different address on every boot, so a literal address in the Lean would change every time, and every proof would be checked again. Instead the generator names addresses. One inside the dictionary is a word's address plus an offset. One in reserved memory is the top of the dictionary less an offset. Proofs can't see the real values, so they hold wherever the dictionary lands.

The output is split into a module per boot file, each importing only the modules it uses. Change the TCP file, and only what depends on it is proven again.

Some words can't be expressed yet. The generator leaves each out, and every word that calls one, and says why. When this lecture was written, that was fifteen colon words of five hundred and eighty-two. They compile code fields, or define words with does. The outer interpreter itself, with comma, parse and search list beneath it, is modelled. Run the generator and read its report for today's list.

The model

structure S where
  ds  : List Cell
  rs  : List Cell
  mem : Mem
  up  : Cell                    -- the current task's user area (x23)
  ext : Nat                     -- outside events so far: pauses, clock reads, I/O
@[forth] def plus   : Sem := bin (· + ·)
@[forth] def pause : Sem := fun s => .ok { s with mem := worldMem s.ext s.mem, ext := s.ext + 1 }
proofs/OS4/Machine.lean
  • Stacks as lists, top first; memory as bytes, little endian
  • Each primitive a function, written to mirror its assembly
  • The outside world unknown: what other tasks, devices and the clock do
  • CATCH and THROW specified; EXECUTE calls an unknown dispatch
  • Every assumption listed in the header

Machine dot lean is the model the generated words run on. The machine's state is five things: the data stack, as a list with the top first; the return stack; memory, as bytes; the task's user area; and a count of outside events.

Each primitive is a function from state to state, or to a failure, written to mirror its assembly. Plus takes two items and pushes their sum, modulo two to the sixty-four. Fetch reads eight bytes, little endian.

The world outside the task is unknown. When a task pauses, other tasks and devices may change any memory, and the clock and the console give unknown answers. Each is an opaque function of the event count, so a theorem holds whatever the world does.

Catch and throw reach below their own frame on the return stack, which this model can't express, so they're replaced by specifications, and execute calls an unknown dispatch. The header of the file lists every such assumption. They're what we trust without proof.

Certificates and bridges

theorem thread_spec {code : List Ins} {cert : List Cert} {inp out : Nat}
    (hchk : check code cert inp out = true) (hcalls : CallsMeet code cert) :
    Spec (thread code) inp out 0 0 := by
proofs/OS4/Spec.lean › thread_spec

All three kinds of generated proof are built the same way. The generator works out a certificate for each word: a fact about the machine before each of its instructions. Lean checks the certificate by computation, with decide: each instruction must take its own fact to its successors'. Then a bridge theorem, proven once by hand, by induction over the thread interpreter, says that a checked certificate, and callees that meet their own theorems, give the word its theorem.

Two things make this work. A word's proof uses its callees' theorems and never unfolds their code, so the cost doesn't grow with how deep the calls go. And the generator doesn't need to be right. If it infers a wrong certificate, the check fails. Only the bridge has to be right, and Lean has checked that.

Stack effects

def Spec (f : Sem) (k j rk rj : Nat) : Prop :=
: min     ( n1 n2 -- n )  2dup > if swap then drop ;
-- depths before: 2dup  >  0branch  swap  drop  exit
noncomputable def «min».cert : List Cert := [⟨Bool.true, 2, 0, 2, 4, 0, 0⟩,
  ⟨Bool.true, 4, 0, 2, 1, 0, 0⟩, ⟨Bool.true, 3, 0, 0, 0, 0, 0⟩,
  ⟨Bool.true, 2, 0, 2, 2, 0, 0⟩, ⟨Bool.true, 2, 0, 1, 0, 0, 0⟩,
  ⟨Bool.true, 1, 0, 0, 0, 0, 0⟩]
theorem «min».spec : Spec «min» 2 1 0 0 :=
  thread_spec (code := «min».code) (cert := «min».cert)
    (by decide)
    (And.intro «2dup».spec (And.intro «>».spec …))
theorem «min».comment : Spec «min» 2 1 0 0 :=
  spec_frame «min».spec 0
proofs/OS4/Specs/Core.lean, generated (wrapped here)
  • Takes k items, leaves j; touches nothing below; the user area kept
  • The certificate: both stacks' depths before each instruction
  • Primitives' effects proven from their models (PrimSpecs.lean)
  • Every plain stack comment checked against the code
  • build/proof-findings.txt: words with no fixed effect, or a comment that disagrees

The first kind is the stack effect. Spec of a word, k, j, says: given k items, if the word returns, it leaves j items in their place, touches nothing below them, and leaves the user area alone. The other two numbers are the same for the return stack. Errors are allowed: this is about shape, not success.

Here's min, and what the generator wrote for it. The certificate lists the depth before each instruction. Two items before two-dup, which takes two and leaves four. Four before greater-than, which leaves three. Three before the branch, which pops its flag. Two before swap, two before drop, and one at exit. Each entry also names the effect its callee must meet, and the proof passes in the callees' own theorems, two-dup's, greater-than's, and so on.

The primitives' effects are proven straight from their models, case by case, in prim specs dot lean.

Then each word's stack comment is read, and if it says something plain, like two items in and one out, it's proven too. That's two hundred and sixty-four comments, and none disagree with their code. Some words can't have a fixed effect yet: those whose effect depends on their data, like question-dup, and those that call through a vector, like type. The findings file lists each word whose comment couldn't be proven, with the reason, and it would list any comment that disagrees. That's a bug, in the comment or the code.

Steps between pauses

def Cost (f : SemT) (n m : Nat) (p : Bool) : Prop :=
  m ≤ allowance → ∀ s b, b ≤ allowance → n ≤ b → Post n m p b (f s b)
proofs/OS4/Yield.lean › Cost
theorem «net-loop».cost : Cost «net-loop».t 3389 3389 Bool.true :=
  threadT_cost (code := «net-loop».tcode) (cert := «net-loop».tcert) (by decide)
theorem «serve-door».cost : Cost «serve-door».t 1010 1010 Bool.true :=
proofs/OS4/Costs/NetNet.lean and NetRepl.lean, generated
  • The watchdog stops a task that runs too long without pausing
  • Counted in Forth instructions: each cell a step, pause refills
  • Cost: at most n steps before the first pause, m between pauses
  • The network task: at most 3389 between pauses, however many connections

The second kind is about the watchdog from lecture five. A task that runs too long without pausing is stopped. For a session that's an error. For the network task, it would stop the network.

Yield dot lean runs the same threads a second way, counting steps. Each cell of a thread is one step, a primitive included, and pause gives the task its whole allowance back. Cost of a word, n, m, says it takes at most n steps before it first pauses, and at most m between pauses or after the last one. The certificate gives the steps spent before each instruction, and a bridge theorem, built like the one for stack effects, turns it into the word's cost.

The system tasks' loops are the roots. The network loop is proven to run at most three thousand three hundred and eighty-nine Forth instructions between pauses, and each door's listener at most one thousand and ten, however many connections there are, whatever arrives.

Proving these found two real problems. The TCP timer sweep walked every connection, up to two hundred and fifty-six, each perhaps retransmitting, without pausing once. And a door's listener accepted every waiting connection in one go. Both pass every test, because tests don't open hundreds of connections. Both now pause after each connection, and the sweep holds a lock so the connection it goes to next can't be freed while it waits.

The yields file says what the proofs start from: the roots, the tables of execution tokens that some words execute from, and the loops that never pause. Those are left out of the count, each with a comment saying what bounds it: a frame's length, the size of a pool. Those bounds are argued, not yet proven.

And any other loop without a pause, on the path of a system task, fails the build. So a new one has to pause, or be listed with its reason.

Footprints: what a word may write

inductive Val where
  | any                         -- unknown
  | arg (i : Nat) (k : Cell)    -- data input i (0 the top) plus k
  | user (k : Cell)             -- the user area plus k
  | kaddr (n : String) (k : Cell) -- a kernel variable's address plus k
proofs/OS4/Footprint.lean › Val
: claim    ( -- )
  begin dict-owner @ dup up@ <> and while pause repeat  up@ dict-owner ! ;
theorem «claim».foot : Foot «claim» 0 0 0 0
    [⟨(.kaddr "dict-owner" 0), (.num 8)⟩] [] [] :=
proofs/OS4/Foots/Core.lean, generated
  • Symbolic values: an input plus k, the user area plus k, a word's address
  • Regions: bytes from a base, for a length
  • build/footprints.txt: 544 words write nothing, 80 "anywhere"
  • The task's own writes: not what others change across a pause

The third kind says what a word may write. A footprint is a list of regions, each some bytes from a base address, and the theorem says every byte outside them keeps its value. It also says where the word's outputs came from. Both are written in symbolic values, relative to the word's entry: an input plus an offset, the user area plus an offset, a word's address, a kernel variable's, a number, or unknown.

Claim, from the lecture on tasks, waits until no other task owns the dictionary, then takes it. Its proven footprint is one region: the eight bytes of dict-owner. Nothing else, though it loops and pauses. +! writes only the cell at its address input. Ms writes only its own task's status and wake time.

The footprints file lists every word's. Most write nothing. Sixty-three may write anywhere. That's safe, not wrong: it means the address was read from memory or computed in a loop, and the generator can't follow it. Those are where a proof by hand is needed.

The writes counted are the task's own. While it pauses, other tasks and devices change what they like, so the theorem is about addresses the outside world leaves alone. In the Lean, that's called quiet.

Proofs by hand: what a word computes

theorem min (a b : Cell) :
    Words.«min» ⟨b :: a :: s, r, m, u, e⟩ = .ok ⟨(if a.slt b then a else b) :: s, r, m, u, e⟩ := by
  forth_auto
proofs/OS4/Core.lean › min
  • For all 2128 pairs of inputs, not a sample
  • forth_auto: run symbolically, split each branch, settle each case with bv_decide
  • within is the one-comparison trick; / by zero fails; the standard's ambiguous division, pinned

The generated proofs are about shape: depth, steps, places written. What a word actually computes needs a theorem written by hand. Core dot lean has them for the stack and arithmetic words. This one says that min, on any two cells, leaves the smaller as a signed number, and nothing else changes.

The proof is one tactic. It runs the word symbolically, splits each branch it takes, and hands each case to a bit-vector solver, which settles it for every possible input. That's every pair of sixty-four-bit numbers, not a sample.

The same file proves that within, the usual trick with one unsigned comparison, means low at most n, less than high, whenever low is at most high. That dividing by zero fails. And what the one ambiguous case of division gives: the most negative number divided by minus one.

proofs/OS4/Refs.lean
  • Hot spots in assembly keep their Forth as the reference
  • fill-ref does exactly what the fill primitive's model does
  • So it writes only its u bytes at addr, where the generator said "anywhere"

From lecture two: when a word moves to assembly for speed, its Forth definition stays as the reference. Fill ref is the Forth version of fill. A test checks they agree on some inputs. This theorem says they agree on all of them.

It says that fill ref, run on any address, count and character, gives exactly the state the fill primitive's model gives. The proof follows the loop by induction, one pass at a time.

And it pays off at once. The generated footprint for fill ref is anywhere, because it stores through an address computed in a loop. From the equality, a second theorem gets the exact footprint: the u bytes from the address, and nothing else. That's the pattern for every word that writes through a computed address.

Sandbox isolation

theorem interpret_isolated (B : Box) (hB : B.Ok)
…
    (d : Cell → Sem) (hd : ∀ xt, B.Allowed xt → d xt = dispatch xt)
    (s : S) (hu : s.up = B.p) (hm : s.mem = B.m0) :

proofs/OS4/Isolation.lean › interpret_isolated
  • EXECUTE replaced by anything that agrees on the sandbox's xts: the same result, for any line
  • An invariant at each of INTERPRET's 49 instructions, checked one instruction at a time
  • Frames: parse-name writes only >in, number? only base
  • Still assumed: the sandbox's own words keep the setting

The brief's hard rule says a player-facing wordlist must never reach the full dictionary. Here it is as a theorem about interpret, as compiled. In the model, execute is an unknown function. So the theorem says: take interpret, and replace its execute with anything at all that agrees with the real one on the sandbox's words. The result is the same, whatever the line holds. So nothing outside the sandbox can make a difference, which means nothing outside it runs.

The proof is an invariant: a statement at each of interpret's forty-nine instructions about what the stack holds. After find name, the top is zero or one of the sandbox's headers. That header is followed to name to x t and execute. And state is zero, so the compiling branches are never reached. Each instruction is checked on its own.

For that, the invariant must survive every word interpret calls. Frames show what each may write: parse name only the to in cell, number only base, the rest nothing. None of those touch the search order, state, or the sandbox's headers.

One thing is still assumed: that the sandbox's own words, when they run, keep that setting. That's the next theorem, word by word, from their footprints.

Running the proofs

docker run --rm -v "${PWD}:/src" -v os4-lake:/src/proofs/.lake os4 make proofs           # everything
docker run --rm -v "${PWD}:/src" -v os4-lake:/src/proofs/.lake os4 make proofs-extract   # just generate
  • Nothing changed: seconds
  • A late boot file changed: about a minute
  • core.fs or the model changed: several minutes
  • Not yet in make test (TD-30): run it at each milestone and before a merge
  • build/proof-findings.txt: stack comments that disagree; words with no fixed effect
  • build/yields.txt: each root's bound, and what is not counted
  • build/footprints.txt: what each word may write

One command runs it all, in the same Docker image as everything else. The second volume keeps Lake's build directory, thousands of small files, off the slow bind mount, and between runs, so only what changed is proven again. Make proofs extract just generates the Lean, if you want to read it.

With nothing changed, a run takes seconds. A change to a late boot file, say the REPL, re-proves its own module and those after it, in about a minute. A change to core dot fs, or to the model, which everything imports, re-proves everything and takes several minutes. That's why the proofs are not yet part of make test. They're run at each milestone and before merging a change to the base.

After a run, read the three reports. The findings first: a stack comment that disagrees with its code is a bug in one or the other. Then the step bounds, and the footprints.

When a proof fails

  • A new primitive: a model in Machine.lean, its effect in PrimSpecs.lean, its footprint in FootPrims.lean, entries in forth2lean.py's PRIMS and EFFECTS (and PRIM_FOOTS if it writes or moves values). Until then, every word that uses it is left out
  • A loop that never pauses on a system task's path: make it pause, or list it in proofs/yields.txt with what bounds it
  • A theorem stops holding: the code's behaviour changed. Fix the code, or restate the theorem if the change was meant
  • Never sorry. An unproven theorem is a missing theorem, not a placeholder

A few failures come up again and again. A new assembly primitive has no meaning in Lean until it's given one: a model in the machine file, its stack effect proven, its footprint proven, and entries in the generator's tables. Until then, the generator leaves out every word that uses it, and says so.

A new loop that never pauses, somewhere the network task or a listener can reach, fails the step counts. Either it pauses, or it goes in the yields file, with a comment saying what bounds it.

A hand-written theorem that stops holding means the word now does something else. That's the point. If the change was a mistake, fix the code. If it was meant, state the new behaviour.

And never write sorry, Lean's way of skipping a proof. A theorem with sorry in it proves nothing, and the build must say so.

What is trusted, and what comes next

  • Trusted (TD-31): the primitives' models, CATCH and THROW's specifications, the dumper and the generator's decoding, Lean's kernel
  • And one abstraction: the world outside the task is unknown
  • A wrong certificate only fails; a wrong decoding would prove the wrong word
  • Next: proofs fast enough for make test; what words read
  • Before players: the sandbox's own words keep it isolated; a stopped task leaves nothing broken; crash-safe records; the MUD's own proofs
  • Before the internet: the network survives any input
  • Depth: TCP's state machine, primitives against the assembly, cryptography

Every proof rests on something unproven, and here it's written down. The models of the primitives, written to mirror the assembly but not proven against it. The specifications of catch and throw. The dumper, and the generator's decoding of threads. And Lean's own kernel. Plus one deliberate abstraction: whatever is outside the task is unknown, so theorems hold whatever it does.

Notice the difference between the generator's two jobs. If it infers a wrong certificate, the check fails, so that part needn't be trusted. If it decoded a thread wrongly, Lean would prove things about the wrong word. That's why the decoding is kept small, and listed as trusted.

The verification plan sets the order of what's next. First, proofs fast enough to run on every change, and footprints for what words read. Before players arrive: that the sandbox's own words keep it isolated, that a task stopped at any point leaves nothing broken, that records survive a crash, and proofs for the MUD itself.

Before the system faces the internet: that the network survives any input. And later, for depth: the TCP state machine, the primitives against their assembly, and the cryptography.
