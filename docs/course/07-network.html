Network I: up to UDP

A network stack in about 400 lines of Forth: Ethernet frames, ARP, IP, ping, and UDP datagrams.

  • The network HAL, and the task that receives every frame
  • Ethernet, byte order, the Internet checksum, ARP and IP
  • ICMP and UDP, and how packets are sent

OS 4.0 has its own network stack, written from scratch in Forth. This lecture covers everything below TCP: about four hundred lines that turn raw Ethernet frames into ping replies and UDP datagrams.

We'll start with the network HAL and the network task, which receives every frame. Then the layers in turn: Ethernet, with network byte order and the Internet checksum; ARP, which finds the hardware address for an IP address; and IP itself.

Then two protocols on top of IP, ICMP for ping and UDP for datagrams, and finally how a packet is built and sent without two tasks treading on each other. Lecture eight does TCP.

The shape of the stack

  • Incoming: one task, one frame at a time, each under its own catch
  • Outgoing: any task, building in a shared frame under a lock

Here's the shape of the whole stack. At the bottom is the network HAL: four words to ask whether there is a network, get its hardware address, send a frame, and poll for a received one.

One task, the network task, receives everything. For each frame it calls frame-in, which looks at the Ethernet type and hands the frame to ARP or to IP. IP checks the packet and hands it to a handler chosen by its protocol number: ICMP, UDP or TCP. All of that happens inside the network task, one frame at a time, and each frame is handled under its own catch, as you saw in lecture five.

Sending is different. Any task can send: a ping from the console, a UDP reply, a telnet session's output. They all build packets in one shared frame, so they take turns, under a lock.

The network HAL on virtio

: net-poll  ( addr -- len )
  net-up? 0= if drop 0 exit then
  rx-vq vq-used? 0= if drop 0 exit then
  rx-vq vq-take  /net-header - >r              ( addr id )
  tuck rx-buf /net-header + swap r@ cmove
  rx-post  r> ;
hal/virtio-net.fs › net-poll
  • 64 receive buffers wait on queue 0
  • Poll: copy a used buffer out, give it straight back
  • Send: one frame at a time on queue 1, and wait
  • Hosted: frames travel as UDP datagrams to a peer

On bare metal, the network card is a virtio device, using the same virtqueues as the disk. At start-up the driver gives the device sixty-four receive buffers, so frames can arrive while the system is busy.

Polling, shown here, checks whether the device has filled a buffer. If it has, the frame is copied out, past a small virtio header, and the buffer goes straight back to the device for the next frame. If not, it returns zero, and the network task sleeps until the next tick.

Sending uses the second queue: copy the frame into the transmit buffer, submit it, and wait for the device to take it.

The hosted build has no network card, so its HAL carries each frame as a UDP datagram to a partner program on the host. The tests use exactly that to put a scripted network peer on the other end, as lecture eleven shows.

Every frame starts here

: frame-in  ( len -- )
  1 frames-in +!
  dup /eth < if drop exit then
  rx-frame eth-type + n16@
  dup type-arp = if  drop rx-frame /eth + swap /eth - arp-in exit  then
  type-ipv4 = if  /eth - ip-in  else drop then ;
forth/net/net.fs › frame-in
  • Too short for an Ethernet header: dropped
  • ARP or IPv4 by the type field; anything else ignored
  • Every layer checks lengths before it trusts them

The network task's loop calls frame-in for every frame it receives. It counts the frame, then checks the first thing anyone attacking the system would try: is the frame even long enough to hold an Ethernet header? If not, it's dropped.

Then it reads the type field. ARP frames go to arp-in, IPv4 to ip-in, each given the payload after the header and its length. Anything else, IPv6 for instance, is ignored.

That first length check is a pattern you'll see at every layer. Each layer is handed a length, and checks every length it finds inside the packet against it, before using any of them. A frame that claims to be longer than it is can never make the stack read past the end of its buffer.

Ethernet, and network byte order

: n16@  ( addr -- u )  dup c@ 8 lshift  swap 1+ c@ or ;
: n16!  ( u addr -- )  over 8 rshift over c!  1+ c! ;
forth/net/eth.fs › n16@
  • Network order: most significant byte first
  • ARM is little-endian, so every field goes through n16@ n32@
  • Fields are named offsets: rx-frame eth-type + n16@

An Ethernet frame starts with two six-byte hardware addresses, called MAC addresses, the destination first, then a two-byte type, then the payload.

Numbers on the network are sent most significant byte first, which is called network byte order. The ARM processor stores numbers the other way round, least significant byte first. So the stack never reads a network field with an ordinary fetch. It uses these words, which assemble the bytes in the right order: N-sixteen-fetch and store for two-byte fields, and the thirty-two-bit versions built on them.

And the fields themselves are just named offsets, constants for the position of each field within its header. Reading the type is: the received frame, plus the type offset, N-sixteen-fetch. Each header file starts with a table of these, which doubles as a picture of the header.

The Internet checksum

: sum16  ( sum addr u -- sum' )  \ add the bytes as 16-bit words, padding an odd one
  begin dup 1 > while  over n16@ >r rot r> + -rot  2 /string  repeat
  if c@ 8 lshift + else drop then ;
: fold   ( sum -- u16 )  \ the checksum of a sum
  begin dup 16 rshift while  dup $ffff and swap 16 rshift +  repeat
  invert $ffff and ;
: checksum  ( addr u -- u16 )  0 -rot sum16 fold ;
forth/net/eth.fs › checksum
  • Add the data as 16-bit words; fold the carries back in; invert
  • Checking is the same sum: a packet with the right checksum sums to 0
  • Split in two so UDP and TCP can add a pseudo-header

IP, ICMP, UDP and TCP all protect their headers with the same simple checksum. Here's all of it.

Sum sixteen adds the data up as sixteen-bit numbers, padding an odd last byte. Fold takes the sum, adds any carries above sixteen bits back into the bottom, which is called one's complement addition, and inverts the result.

The neat property is that checking uses the very same computation. Run the checksum over a packet that includes a correct checksum field, and the answer is zero. So every receiver just checks for zero.

It's split into two words for UDP and TCP. Their checksums also cover a pseudo-header, made of the addresses from the IP header, which isn't part of the segment itself. Keeping the sum and the fold separate lets them add the pieces one after another.

ARP: who has 10.0.2.2?

: on-link?  ( ip -- flag )  my-ip @ xor netmask @ and 0= ;
: next-hop  ( ip -- ip' )  dup on-link? 0= if drop gateway @ then ;
: resolve   ( ip -- mac | 0 )  \ 0 if not yet known; an ARP request has then gone out
  dup broadcast-ip = if drop broadcast-mac exit then
  next-hop  dup arp-find ?dup if nip exit then
  arp-request 0 ;
forth/net/arp.fs › resolve
  • Off our network? Then the gateway's MAC
  • An 8-entry cache, replaced round robin
  • Not known: broadcast a request, return 0; the caller tries again
  • Learns only from packets addressed to us, never a group address

To send an IP packet over Ethernet, you need the MAC address of the next machine along the way. ARP, the address resolution protocol, finds it by broadcasting a question to the whole local network: who has this IP address? The owner replies with its MAC.

Resolve is where the stack asks. A broadcast address needs no lookup. Otherwise, work out the next hop: if the destination is on our own network, it's the destination itself; if not, it's the gateway. Then look in a small cache of eight recent answers.

If it's not in the cache, resolve sends an ARP request and returns zero, meaning not yet. It doesn't wait. The caller tries again a little later, by which time the reply has usually arrived and been learned.

Learning is careful too. The cache only learns from packets addressed to us, and never accepts a multicast or broadcast address as anyone's MAC. That makes it harder for a stranger on the network to fill the cache with lies.

IP: trust nothing, check every length

: ip-check  ( len -- ihl total true | false )  \ a whole, unfragmented packet for us
  rx-ip ip-ver-ihl + c@  dup 4 rshift 4 <> if  2drop false exit  then
  15 and 4 *  2dup <  over /ip < or if  2drop false exit  then      ( len ihl )
  rx-ip over checksum if  2drop false exit  then
  rx-ip ip-length + n16@  rot over < if  2drop false exit  then    ( ihl total )
  2dup > if  2drop false exit  then
  rx-ip ip-fragment + n16@ $3fff and if  2drop false exit  then
  rx-ip ip-dst + n32@  dup my-ip @ =  swap broadcast-ip = or 0= if  2drop false exit  then
  ip-source bad-source? if  2drop false exit  then
  true ;
forth/net/ip.fs › ip-check
  • Version 4; a header length that fits the frame and the minimum
  • The header checksum; a total length within the frame and past the header
  • No fragments; for us or a broadcast; not from an impossible source

IP is where the stack is most careful, because every packet from the outside world passes through here. Ip-check reads like a list of rules, and any rule broken drops the packet silently.

The version must be four. The header length must fit within the frame, and be at least the minimum of twenty bytes. The header checksum must be right. The total length the packet claims must fit within what actually arrived, and be at least the header's own length.

Then: no fragments, because OS 4.0 doesn't reassemble them, and simply refuses them. The destination must be our address or the broadcast address. And the source mustn't be one that no real machine can have, such as our own address, or a multicast address.

Only after all that does the packet reach a protocol handler. The hostile-input test sends hundreds of malformed and random frames at exactly these checks.

Protocols plug in

: ip-handler!  ( xt protocol -- )  cells ip-handlers + ! ;
forth/net/ip.fs › ip-handler!
: icmp-in  ( message len -- )
  dup /icmp-echo <  if 2drop exit then             \ every ICMP message has 8 bytes of header
  2dup checksum if 2drop exit then
  over icmp-type + c@  dup 8 = if drop echo-reply exit then
  0= if echo-in else 2drop then ;
' icmp-in proto-icmp ip-handler!
forth/net/icmp.fs › icmp-in
  • A table of 256 handlers, by protocol number
  • ICMP: answer echo requests (ping), note replies to ours
  • A protocol nobody handles: ICMP "protocol unreachable"

IP doesn't know about the protocols above it. Instead it has a table of two hundred and fifty-six handlers, one per protocol number, and each protocol file registers itself with ip-handler-store, as the last line of the ICMP code here does.

ICMP is the control protocol, best known for ping. Its handler checks the length and the checksum, then looks at the type. Type eight is an echo request, a ping, and gets an echo reply with the same data. Type zero is a reply to one of our own pings, which the ping word is waiting for.

If a packet arrives for a protocol that has no handler, the stack replies with an ICMP message saying protocol unreachable, as a well-behaved host should. Likewise, UDP will answer port unreachable for a port that nobody is listening on.

UDP: datagrams to ports

7 constant echo-port
: echo  ( data len -- )  udp-reply drop ;
: echo-service  ( -- )  ['] echo echo-port udp-bind ;
forth/net/udp.fs › echo-service
  • xt port udp-bind: datagrams to that port go to xt
  • Handlers run in the network task: be quick, don't wait
  • udp-peer-ip, udp-peer-port, udp-reply: about this datagram
  • The checksum is checked if present, and always sent

UDP adds port numbers to IP, and a length and a checksum, and that's all: each datagram stands alone, with no connection and no guarantee it arrives.

An application binds a port to an execution token. Here's the echo service from the standard, in three lines: bind port seven to a word that sends every datagram straight back with udp-reply.

One thing to know about UDP handlers: they run inside the network task, in the middle of receiving. So they must be quick and must never wait. Anything slow should be handed to a task of its own. While a handler runs, words like udp-peer-ip and udp-reply refer to the datagram being handled.

On the way in, the checksum is checked if the sender included one; on the way out, one is always sent.

Sending: one frame, one lock

\ A task that builds and sends a packet holds TX-LOCK from start to finish, as
\ every sending word below does: building in the shared frames (tx-frame and
\ ARP's) and sending, which may pause while the device works.
semaphore tx-lock
: udp-send  ( data len port dst-ip dst-port -- flag )  ['] (udp-send) tx-lock locked ;
forth/net/udp.fs › udp-send
  • Packets are built in place in tx-frame: no copying between layers
  • The lock covers building and sending
  • A false flag: the MAC wasn't known; an ARP request went out; try again

Outgoing packets are built in place, in one shared frame buffer called tx-frame. UDP writes its header and data where they'll sit in the final frame; IP writes its header in front; Ethernet fills in the addresses; and the frame goes to the HAL. Nothing is copied from layer to layer.

Because that frame is shared, a task holds tx-lock from the first byte it builds to the moment the frame is sent. Sending can pause while the device works, and without the lock another task could start building its own packet over the top. That was once a real risk, written up in the tech debt register; the lock closed it.

Notice that udp-send returns a flag. False means the destination's MAC address wasn't known yet, so an ARP request went out instead. The caller waits a moment and tries again, as the ping word does.

Try it on the console

.net                                   \ address, MAC and gateway
ip 10.0.2.2 ping                       \ three echo requests
echo-service                           \ answer UDP echo on port 7
: heard  ( data len -- )  ." heard: " type cr ;
' heard 5000 udp-bind                  \ datagrams to port 5000 go to HEARD
s" hello" 5000 ip 10.0.2.2 7 udp-send drop
.net-stats                             \ frames in and out

The OS is 10.0.2.15 on QEMU's user network; the gateway is 10.0.2.2. make ping-check pings it with the real ping.

Boot the bare-metal build and try these. Dot-net shows the address, the MAC and the gateway. Ping the gateway. Start the echo service on port seven.

Then bind a port of your own to a word that prints whatever arrives, and send a UDP datagram to the gateway's echo port. Dot-net-stats shows the frames going in and out, and how many ARP requests and pings have been answered.
