Network II: TCP

A reliable byte stream from unreliable packets, for servers, in about 500 lines of Forth, and hardened against attackers it never meets.

  • Connections, the handshake, and counting bytes
  • Receiving, sending, loss and closing
  • Defences against off-path attackers, and the application's view

TCP is the protocol behind telnet, the web, and nearly everything else. It turns IP's packets, which can be lost, duplicated or reordered, into a reliable stream of bytes in each direction. OS 4.0's TCP is about five hundred lines of Forth, and it's built for servers: it accepts connections, it doesn't make them.

We'll look at how a connection is set up, and at one design choice that keeps the code simple: counting bytes instead of juggling sequence numbers. Then how segments are received and sent, how lost ones are resent, and how a connection closes.

Finally, how it defends itself against attackers who can send packets but can't see the conversation, and what all of it looks like to the application.

The design, in its own words

\ net/tcp.fs: TCP, for servers. LISTEN on a port; connections that complete the
\ handshake queue for ACCEPT-CONNECTION. The application uses SEND, SEND-LINE,
\ GET-LINE and CLOSE-CONNECTION, sleeping while it waits; the network task wakes
\ it when something changes. Lost segments are resent, go-back-N, with an
\ exponentially growing timeout. Out-of-order segments are dropped: the sender
\ resends them.
forth/net/tcp.fs
  • The network task handles segments; application tasks sleep until woken
  • Simple where it can be: go-back-N, in-order only
  • Careful where it must be: every number from outside is checked

The top of the TCP file describes the whole design in six lines, so let's start there.

An application listens on a port. Connections that complete the handshake wait in a queue until the application accepts them. It then sends and receives lines, and closes. Whenever it has to wait, it sleeps, and the network task wakes it when something changes. That's the split: the network task does all the protocol work, and application tasks just sleep and wake.

Two simplifications keep the code small. Lost segments are resent go-back-N: everything from the oldest unacknowledged byte goes again. And segments that arrive out of order are dropped rather than buffered; the sender will resend them. Both cost a little speed on a lossy network, and save a great deal of code.

Where it can't be simple is in what it believes. Every number in a segment comes from outside, and is checked before it's used.

Opening: the handshake, and the accept queue

  • SYN, SYN-ACK, ACK: all in the network task
  • The application only ever sees established connections
  • Empty queue: the listener stops; enqueue wakes it
: accept-connection  ( port -- conn )  \ wait for the next connection on port
  listener-of dup 0= if -24 throw then
  begin dup cell+ @ 0= while  up@ over 2 cells + !  stop  repeat
  0 over 2 cells + !
  cell+ dup @ tuck c.next @ swap !
  up@ over c.owner ! ;
forth/net/tcp.fs › accept-connection

A TCP connection opens with a three-way handshake. The client sends a SYN, a segment asking to synchronise. The server answers with a SYN-ACK: its own SYN, and an acknowledgement of the client's. At that point the connection is half open, in a state called syn-received. When the client's final ACK arrives, the connection is established.

All of that happens in the network task. The application doesn't see a connection until it's fully established: only then is it added to the listening port's queue.

Accept-connection takes the next one from that queue. If the queue is empty, the task records itself as the one waiting, and stops. When the network task queues a new connection, it wakes the waiting task, which takes the connection and records itself as its owner, the task to wake whenever anything changes on it.

Counting bytes, not sequence numbers

1 cells field c.tx-acked          \ bytes they have acknowledged
1 cells field c.tx-sent           \ bytes sent, acknowledged or not
1 cells field c.tx-queued         \ bytes the application has given us
1 cells field c.rx-in             \ bytes received in order
1 cells field c.rx-out            \ bytes the application has taken
: snd-nxt  ( conn -- seq )
  dup c.iss @ 1+ over c.tx-sent @ +  swap fin-sent flag? if 1+ then  $ffffffff and ;
forth/net/tcp.fs › snd-nxt

On the wire, TCP numbers every byte with a thirty-two-bit sequence number that starts at a random point and wraps round. Comparing those numbers is a notorious source of bugs.

So inside, a connection counts bytes instead, from zero, in sixty-four-bit cells that never wrap. On the sending side: bytes the other end has acknowledged, bytes sent, and bytes the application has queued. On the receiving side: bytes received in order, and bytes the application has taken.

Everything else follows from the differences. Sent minus acknowledged is what's in flight. Queued minus sent is what's still to send. And a count, masked to the ring's size, is a position in the connection's transmit or receive ring.

Sequence numbers are only made at the edge, when a segment goes out or comes in. Send-next is the initial sequence number, plus one for the SYN, plus the bytes sent, plus one more if our FIN has gone, wrapped to thirty-two bits.

Receiving a segment

: segment-in  ( conn -- )
  >r
  f-rst i-flag? if  r> rst-in exit  then
  r@ c.state @ syn-received = if
    f-syn i-flag? if  r@ dup c.iss @ f-syn f-ack or control-out  r> drop exit  then
    f-ack i-flag? 0=  i-ack @ r@ c.iss @ 1+ $ffffffff and <>  or if  r> drop exit  then
    established r@ c.state !  0 r@ c.rexmit !  base-rto r@ c.rto !  0 r@ c.retries !
    r@ dup c.lport @ listener-of ?dup if enqueue else drop then
  then
  f-syn i-flag? if  r@ ack-now flag+  r> tcp-output exit  then
  f-ack i-flag? 0= if  r> drop exit  then
  r@ ack-ok? 0= if  r> challenge exit  then
  i-wnd @ r@ c.snd-wnd !
  r@ acked
  r@ fin-acked-in
  r@ c.state @ closed = if  r> drop exit  then      \ released, maybe recycled
  r@ receiving? if r@ data-in then
  r@ fin-in
  r@ c.state @ closed = if  r> drop exit  then
  r> tcp-output ;
forth/net/tcp.fs › segment-in

Every segment for an existing connection goes through segment-in. It's the heart of TCP, and it reads from top to bottom. A reset is handled first, with care, as we'll see later.

In blue, the handshake. If the connection is still half open, a repeated SYN means our SYN-ACK was lost, so it's sent again. Otherwise this must be the ACK that completes the handshake, acknowledging exactly our SYN. If it is, the connection is established and queued for the application.

In green, the acknowledgement. A SYN on an established connection is suspicious, and just gets an ACK. A segment without an ACK is dropped. An acknowledgement outside the range we could have sent gets a challenge, coming later. Otherwise, note how much the other end will now take, move the acknowledged count on, and see whether that finished our FIN.

In orange, the rest: take any data, take a FIN if there is one, and finally send whatever is now owed: data, a FIN, or an ACK.

In order, or not at all

: data-in  ( conn -- )  \ in-order data, as much as fits; anything else is dropped
  i-len @ 0= if drop exit then
  dup fin-received flag? if drop exit then
  i-seq @ over rcv-nxt <> if  ack-now flag+ exit  then   \ say where we are
  dup rx-room i-len @ min                           ( conn n )
  dup 0 ?do
    i-data @ i + c@  2 pick c.rx-in @ i + /rx 1- and  3 pick c.rx + c!
  loop
  over c.rx-in +!
  dup ack-now flag+  wake-owner ;
forth/net/tcp.fs › data-in
  • Not the next byte we expect? Drop it, and ACK where we are
  • Take only what fits in the ring: the window we advertised
  • Then owe an ACK, and wake the application

Here's the in-order rule in practice. Data-in accepts a segment only if it starts exactly at the next byte we expect. Anything else, a duplicate or a segment that skipped ahead, is dropped, and we owe the sender an ACK saying where we really are. That ACK is what prompts it to resend.

A segment that does start in the right place is copied into the receive ring, as much as fits. The window we advertise to the other end is the room in that ring, so a well-behaved sender never sends more. A badly behaved one just loses the excess.

Finally, an ACK is owed for the new data, and the owning task is woken: there may now be a whole line for it to read.

Sending: what the window allows

: sendable  ( conn -- n )
  dup unsent  over c.snd-wnd @ 2 pick in-flight - 0 max  min  swap c.mss @ min ;
forth/net/tcp.fs › sendable
  • The least of: what's unsent, the room left in their window, one segment
  • tcp-output sends segments while there is any, then the FIN, then a bare ACK if owed
  • A closed window: the retransmit timer probes it
  • Telnet output follows Nagle's rule: one small segment in flight at a time

Sending is governed by a single question: how much may go now? Sendable answers it. The least of three things: what the application has queued but not yet sent, the room left in the other end's window, which is the window it advertised minus what's already in flight, and one segment's worth, the largest the other end said it accepts.

TCP output sends segments of that size until sendable is zero. Once everything queued has gone, and if the application has closed, it sends our FIN. And if an ACK is owed and nothing else carried it, it sends a bare ACK.

If the other end's window is shut, with data waiting, the retransmission timer is armed anyway, and when it fires it sends a single byte to probe whether the window has opened.

One refinement lives in the telnet layer: output waits while a small segment is still unacknowledged, which is Nagle's rule. Typing and echoing a character at a time would otherwise make a segment per keystroke.

When segments are lost

: retransmit  ( conn -- )  \ from the oldest unacknowledged byte, with a longer timeout
  dup c.retries @
  over c.state @ syn-received = if max-syn-retries @ else max-retries then
  < 0= if                                           \ give up
    dup dup snd-nxt f-rst control-out  release-conn exit
  then
  1 over c.retries +!
  dup c.rto @ 2* max-rto min over c.rto !
  …
  dup c.tx-acked @ over c.tx-sent !
forth/net/tcp.fs › retransmit
  • The timeout starts at 1 s and doubles, up to 60 s
  • Go-back-N: "sent" goes back to "acknowledged", and sending starts again
  • After 8 tries (4 for a half-open connection), reset and give up

Each connection has a retransmission timer, armed whenever data is in flight. Once a tick, the network task sweeps every connection's timers, and pauses after each one, so a thousand connections never hold up the other tasks. While it sweeps, it holds a lock that freeing a connection also takes, so no other task can free the one it goes to next. If a timer has expired, retransmit runs.

First, has this connection tried too often? After eight attempts, or four for one that's still half open, it sends a reset and gives up. Otherwise it counts the attempt, and doubles the timeout, starting at one second and capped at a minute. Doubling is what keeps a struggling network from being flooded with retries.

Then the go-back-N step, which is the last line here, and it's the whole of it. Set the sent count back to the acknowledged count. As far as the connection is concerned, everything in flight was never sent, so the next call to TCP output sends it again from the oldest unacknowledged byte. Counting bytes makes this a single store.

Closing

: close-connection  ( conn -- )
  dup app-closed flag+
  dup c.state @ closed = if  free-conn exit  then
  linger-ms deadline over c.timeout !
  dup fin-queued flag+  tcp-output ;
forth/net/tcp.fs › close-connection
  • The FIN goes after everything queued; a minute to get it out, then a reset
  • Every state that waits on the other end has a timeout

Each direction of a connection closes separately, with a FIN. If we close first, the connection passes through fin-wait-one, until our FIN is acknowledged, then fin-wait-two, until theirs arrives, then time-wait for two seconds, to catch any stragglers. If they close first, we go through close-wait, while the application finishes, and last-ack, until our FIN is acknowledged.

For the application, it's one word. Close-connection marks the connection as given up by the application, sets a linger deadline of one minute, and queues a FIN. The FIN only goes once everything queued before it has been sent.

The important detail is that every state that waits for the other end has a time limit. A client that never acknowledges, or never sends its own FIN, can't hold a connection record for ever: after the linger time, or the fin-wait time, it's reset and recycled.

Defences against off-path attackers

: new-iss  ( -- seq )  \ RFC 6528: a clock, plus a keyed hash of the addresses and ports
  ip-source i-sport @ i-dport @ isn-key tuple-hash  counter 4 rshift +  $ffffffff and ;
: rst-in  ( conn -- )
  i-seq @ over rcv-nxt = if  release-conn exit  then
  i-seq @ over rcv-nxt - $ffffffff and  over rx-room u< if challenge else drop then ;
: room?  ( -- flag )  \ a new connection is within the caps
  conns @ count-list max-conns @ <  half-open max-half-open @ < and ;
forth/net/tcp.fs › new-iss, rst-in, room?
  • Unguessable initial sequence numbers
  • A reset counts only at exactly the next byte; near it, a challenge ACK
  • Caps: 256 connections, 64 half open; a SYN beyond them is dropped
  • A keyed hash table: nobody can aim every connection at one bucket

An off-path attacker can send packets with forged addresses, but can't see the conversation. TCP's defence is that a forged segment must carry sequence numbers the attacker can't know. So they must be unguessable. New-iss makes the initial sequence number from a clock plus a keyed hash of the connection's addresses and ports, as RFC sixty-five twenty-eight recommends. The key is random, drawn at boot.

Resets are the next target, because a forged reset kills a connection. Following RFC fifty-nine sixty-one, a reset only counts if its sequence number is exactly the next byte we expect. One that's merely close gets a challenge ACK instead, which a genuine peer answers with an exact reset, and an attacker never sees.

Then there are floods. The caps allow two hundred and fifty-six live connections and sixty-four half-open ones; a SYN beyond that is simply dropped, and a real client will retry. And connections are found through a hash table keyed with another random key, so an attacker can't choose ports that all land in one bucket and slow every lookup to a crawl.

The application's view

: serve ( conn -- ) begin pad 256 2 pick get-line dup 0< 0= while pad swap 2 pick send-line repeat drop close-connection  1 served +! ;
: line-server ( -- ) 5000 listen begin 5000 accept-connection ['] serve spawn drop again ;
tests/tcp.in
: io-wait   ( -- )  \ sleep until woken; throw -273 if the time is up
  up@ cur-conn @ c.owner !
  io-until @ ?dup if  dup expired? if drop -273 throw then  stop-until  else  stop  then ;
forth/net/tcp.fs › io-wait
  • A line echo server in two lines: a task per client from the pool
  • Waiting words sleep until woken, or until io-timeout: then -273
  • A server must set io-timeout: a client that stops reading can't hold a task

All that machinery disappears behind a few words. Here's the line echo server from the TCP test, in two lines. Line-server listens on port five thousand, and for ever accepts a connection and spawns a pooled task to serve it. Serve reads lines with get-line and sends each one back with send-line, until the client finishes, then closes.

Get-line, send and the rest all wait the same way, through io-wait. The task records itself as the connection's owner and stops; the network task wakes it when data arrives, or when room opens up to send.

There's a time limit on every wait too. If the task's io-timeout is set, a wait that runs past it throws -273. Any task serving a remote client must set one, because otherwise a client that connects and then goes silent, or stops reading, would hold that task for ever. The network REPL sets ten minutes for idle sessions.

Questions to think about…

  1. Out-of-order segments are dropped. On what kind of network does that cost the most, and how would you measure it?
  2. Why does a reset near, but not exactly at, the next sequence number get a challenge ACK rather than being ignored?
  3. serve forgets to set io-timeout. Write the client that exploits it.

That's TCP. Connections are queued only when established, bytes are counted rather than sequence-numbered, segments are taken in order, lost ones are resent go-back-N with a doubling timeout, every waiting state has a limit, and forged segments must guess numbers they can't see.
