Forth in twelve minutes

Just enough Forth to read the rest of the system: the stack, words, the dictionary, and how Forth extends itself.

  • The data stack, and words that work on it
  • The dictionary, and the interpreter that searches it
  • Immediate words and defining words: the language built in itself

This lecture teaches just enough Forth to read the rest of OS 4.0. If you already know Forth, skim it: the examples are all from this system's own source.

We'll start with the stack and the words that work on it. Then the dictionary, where words live, and the interpreter, which reads your input and either runs words or compiles them.

Finally, the two ideas that make Forth unusual: immediate words, which run while a definition is being compiled, and defining words, which make new kinds of word. Between them, most of Forth is written in Forth.

Everything goes through the stack

  • Numbers are pushed; words take their inputs from the top
  • Words run left to right: no brackets, no precedence
  • .s shows the stack without changing it

Forth reads your input as words separated by spaces, and runs them from left to right. Here's the simplest possible example: two, three, plus, dot.

A number is pushed onto the data stack. Two goes on, then three goes on top of it. Plus takes the top two numbers off, adds them, and pushes the result, five. Dot takes the top number and prints it.

That's the whole syntax. There are no brackets and no operator precedence, because there's nothing to decide: each word runs as soon as it's read, and finds its inputs waiting on the stack. Words pass values to each other through the stack, not through named parameters.

When you're experimenting, .s shows the whole stack without changing it. You'll use it constantly.

New words from old

: square  ( n -- n*n )  dup * ;
5 square .            \ 25
: rot    ( a b c -- b c a )  >r swap r> swap ;
: nip    ( a b -- b )  swap drop ;
: tuck   ( a b -- b a b )  swap over ;
: 2dup   ( a b -- a b a b )  over over ;
forth/core.fs › rot
  • The comment in brackets is the stack effect: before, then after
  • Every word in OS 4.0 has one

You make a new word with a colon, its name, the words it should run, and a semicolon. Square duplicates the top of the stack and multiplies, so five square leaves twenty-five.

Most of Forth is built exactly like this. These are the first lines of core dot fs, the first boot file. Rot, nip, tuck and two-dup are all defined from simpler stack words that the kernel provides in assembly. Rot even uses the return stack, which we'll meet shortly, to hold a value out of the way.

The comment in brackets is the stack effect. It shows what the word expects on the stack before the dashes, and what it leaves after. Forth itself ignores it, but every word in OS 4.0 has one, and it's the first thing to read when you meet a new word.

The dictionary: a linked list of words

// Dictionary header, 8-byte aligned:
//   +0  link to the previous header (0 ends the chain)
//   +8  flags: bit 7 immediate, bit 6 hidden, bits 0-4 name length
//   +9  name, padded to 8 bytes
//   then the xt
arch/aarch64/kernel.s

Where do words live? In the dictionary, which is a linked list in memory. Each word starts with a header: a link to the previous word's header, a byte of flags and the name's length, and the name itself. The word's code follows straight after.

A variable called latest points at the newest header. Looking a word up means starting there and following the links back, comparing names, until it's found or the chain ends.

Two consequences are worth remembering. First, defining a word again doesn't replace the old one: the new one is simply found first, by everything compiled afterwards. Words compiled earlier still call the old one. Second, the address of a word's code is its execution token, the xt. It's how Forth refers to a word as a value, to be run later with execute.

Interpreting and compiling

: interpret  ( -- )  \ the current line, word by word
  begin parse-name dup while
    2dup find-name ?dup if
      state @ 0= over compile-only? and if  drop errname 2! -14 throw  then
      nip nip  dup immediate? state @ 0= or if name>xt execute else name>xt , then
    else
      2dup number? 0= if undefined then  nip nip  state @ if postpone literal then
    then ?stack
  repeat 2drop ;
forth/interpreter.fs › interpret
  • Found: run it, or, while compiling, append its xt with ,
  • Not found: a number, pushed or compiled as a literal; else error -13
  • state decides: : turns compiling on, ; turns it off

This is the outer interpreter, the loop that reads what you type. It's written in Forth, and it's short enough to read in full.

It takes the next word from the line and looks it up. If the word is found, there are two choices. Normally it's executed straight away. But if the system is compiling, the word's execution token is appended to the definition being built instead, with the comma word.

If the word isn't found, it might be a number. Then it's pushed, or, when compiling, compiled as a literal that pushes it later. If it's not a number either, that's error -13, undefined word.

What decides between running and compiling is one variable, state. Colon parses a name, lays down a header and turns compiling on. Semicolon compiles an exit and turns it off again. A colon definition is just a list of execution tokens, built one word at a time by this loop.

Immediate words build control flow

: if    ( C: -- orig )  ['] 0branch , here 0 , ; immediate compile-only
: then  ( C: orig -- )  here swap ! ; immediate compile-only
forth/core.fs › if
  • An immediate word runs even while compiling
  • if leaves a hole; then fills it
  • begin until again while repeat do loop: all the same trick
  • So control flow is ordinary Forth, not syntax

Some words are marked immediate. An immediate word runs even while the interpreter is compiling, so it can take part in building the definition. That's how Forth gets control flow without any special syntax.

Look at if. When it runs, during compilation, it appends a conditional branch, then an empty cell, and leaves that cell's address on the stack. The true part is compiled after it as usual. Then then runs, takes the address off the stack, and stores the current position into the empty cell. At run time, the conditional branch jumps there when the flag is zero, skipping the true part.

Begin, until, again, while, repeat, and the counted loops all work the same way, each in a line or two of core dot fs.

So control flow is not built into the compiler. It's ordinary Forth, and you could write new control structures of your own the same way.

Defining words

: create    ( "name" -- )  parse-name header dovar cf, ;
: variable  ( "name" -- )  create 0 , ;
: constant  ( x "name" -- )  parse-name header docon cf, , ;
forth/core.fs › create
: field  ( offset size "name" -- offset' )  create over , +  does> @ + ;  \ name ( addr -- addr' )
forth/core.fs › field
  • create: a header, and code that pushes the body's address
  • does>: what the new words do when they run
  • Used throughout: task, semaphore, user, field

A defining word makes new words. Create is the basic one: it parses a name, lays down a header, and compiles a code field that pushes the address of the word's body. Variable is create followed by one cell of zero. Constant uses a different code field, one that pushes the value stored in the body instead of its address.

The interesting one is does. Field is a defining word for record layouts. When you use it, create makes the new word and stores its offset. The part after does is what every word made by field will do when it runs: fetch the stored offset and add it to an address. So a field named after a part of a record turns a record's address into the address of that part.

You'll find this pattern all over the system. Task, semaphore, user variables, and every record layout are defining words.

Memory: the dictionary grows

: here     ( -- addr )  dp @ ;
: allot    ( n -- )  dp +! ;
: c,       ( c -- )  here c! 1 allot ;
forth/core.fs › here
\ fetch and store
variable count
5 count !         \ store 5
count @ .         \ 5
1 count +!        \ now 6
  • here is the next free byte; allot and , move it on
  • Definitions and data share this one space
  • @ fetches a cell, ! stores one; c@ c! for bytes
  • Running tasks take memory from the far end, with reserve

Forth's memory is simple. The dictionary grows upwards from the bottom of one region. Here is the address of the next free byte, held in a variable called dp. Allot moves it on by some number of bytes, and comma stores a cell there and moves on past it.

Definitions and data share that space. A variable is just a header followed by a cell, made with create and comma.

To use memory, fetch with the at sign and store with the exclamation mark, which Forth calls fetch and store. They work on whole cells, eight bytes here. C-fetch and C-store do single bytes, and plus-store adds to a cell.

One rule specific to OS 4.0. Memory that running tasks need, such as connection records, comes from the far end of the same region, through a word called reserve. Never from allot, because another task might be in the middle of compiling a definition at here.

The return stack

  • >r moves a value there, r> brings it back, r@ copies it
  • do … loop keeps its index there: i reads it
  • Rule: leave it as you found it before the word ends

Forth has a second stack, the return stack. When a word calls another, the place to come back to is pushed here, and exit pops it. That's why the data stack can be left entirely to values.

You can borrow the return stack too. To-R moves a value from the data stack to the return stack, out of the way, and R-from brings it back. R-fetch copies it without removing it. Rot, which we saw earlier, uses exactly this.

Counted loops keep their limit and index there too, and the word i reads the current index.

The rule is that a word must leave the return stack as it found it, because the next thing on it is where the word returns to. In OS 4.0, getting this wrong usually shows up as a return stack error rather than a crash, as lecture four explains.

Try it on the console

2 3 + .                            \ 5
: square  ( n -- n*n )  dup * ;
7 square .                         \ 49
: stars  ( n -- )  0 ?do  [char] * emit  loop ;
5 stars                            \ *****
: sign?  ( n -- )  0< if ." negative" else ." not negative" then ;
-3 sign?
words                              \ every word, newest first

Boot with docker run --rm -it os4, or make run-hosted for an instant start.

Boot the system and try a few of these. Add two numbers. Define square and use it. Stars uses a counted loop to print some asterisks; the question-do form does nothing if the count is zero.

Sign uses if, else and then inside a definition. Remember that if and then only work inside a definition, because they compile branches.

Finally, type words to list everything in the dictionary, newest first. You'll recognise many of the names from this lecture.
